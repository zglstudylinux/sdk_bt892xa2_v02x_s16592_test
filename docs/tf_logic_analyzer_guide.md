## 1. TF 卡的物理结构

### 1.1 一张 TF 卡的解剖

```
              ┌─────────────────────┐
              │ 塑料外壳              │
              │  ┌─────────────────┐ │
              │  │ NAND Flash 颗粒  │ │  ← 实际存数据的地方（和 U 盘芯片一样）
              │  ├─────────────────┤ │
              │  │ 控制器芯片      │ │  ← 跑 SD 协议、做 ECC 校验、做坏块管理
              │  └─────────────────┘ │
              │   8 个金手指（接口）    │
              └─────────────────────┘
```

- **NAND Flash**：存数据的物理介质，但很"笨"——只能按 page/block 读写，要做 ECC、坏块管理
- **控制器芯片**：把 NAND 包装成"标准的 SD 协议接口"，对外屏蔽 NAND 的复杂性

**对我们来说**：直接打交道的是**控制器芯片**（用 SD 协议），看不到 NAND 内部细节。

### 1.2 8 个引脚定义

```
      ┌──────┐
  1 ──┤      ├── 8  (DAT1)
  2 ──┤      ├── 7  (DAT0)
  3 ──┤      ├── 6  (VSS-地)
  4 ──┤      ├── 5  (CLK-时钟)
  5 ──┤      ├── 4  (VDD-电源)
  6 ──┤      ├── 3  (CMD-命令)
  7 ──┤      ├── 2  (DAT3/CS)
  8 ──┤      ├── 1  (DAT2)
      └──────┘
       卡正面看
```

| 引脚 | 名称 | 作用 | 我们用了吗？ |
|---|---|---|---|
| 1 | DAT2 | 数据线 2（4-bit 模式用） | ❌ |
| 2 | DAT3 / CS | 数据线 3（SPI 模式当片选） | ❌ |
| **3** | **CMD** | **命令线（双向）** | **✅ 接到 PE5** |
| 4 | VDD | 电源 2.7~3.6V | ✅ 外部供电 |
| **5** | **CLK** | **时钟（主机输出）** | **✅ 接到 PE6** |
| 6 | VSS | 地 | ✅ |
| **7** | **DAT0** | **数据线 0（双向）** | **✅ 接到 PE7** |
| 8 | DAT1 | 数据线 1（4-bit 模式用） | ❌ |

**我们的测试只用 3 根线：CMD + CLK + DAT0**（1-bit 模式）。

### 1.3 方向：谁驱动谁？

| 线 | 默认方向 | 切换时机 |
|---|---|---|
| **CLK** | **永远是主机输出**（卡是被动的） | 永不切换 |
| **CMD** | 主机发送命令时主机驱动；卡回响应时卡驱动 | 每条命令切换 |
| **DAT0** | 读时卡驱动；写时主机驱动；空闲时双方都不驱动（高阻） | 每次传输切换 |

## 2. SD 卡协议在信号层长啥样

### 2.1 比特（bit）怎么发

SD 模式用的是 **NRZ（不归零）编码** + **同步时钟**：

```
       时钟周期 1   周期 2   周期 3   周期 4
CLK:  ───┐  ┌──┐  ┌──┐  ┌──┐  ┌──
          └──┘  └──┘  └──┘  └──┘  └─...

DAT:  ────────██████────────████────
       周期1  周期2 = 1, 周期3 = 0
```

- **每个时钟周期传输 1 bit**
- **数据在时钟的上升沿被采样**（CLK 从 0 跳到 1 的瞬间，对方读数据线）
- 1 个字节 = 8 个时钟周期 = **MSB 在前**（高位先发，跟 x86 相反！）

### 2.2 字节（byte）怎么发

**MSB 在前**（最高位先发）：

```
字节 0xE8 = 11101000 二进制

主机发送：
  ──┐  ┌─────┐  ┌────┐  ┌─┐  ┌─┐  ┌┐ ┌─┐ ┌─┐ ┌┐ ┌────
    └──┘     └──┘    └──┘  └─┘  └─┘  └┘ └─┘ └─┘ └┘ └────
   1   1   1   0   1   0   0  0  0    ← 8 bit，MSB 在最左
   ↑                               ↑
   bit7 (MSB)                      bit0 (LSB)
```

### 2.3 命令格式（48 bit = 6 字节）

```
主机 → 卡：每次发一条命令永远是 6 字节
[0]   [1]    [2]    [3]    [4]    [5]
0  1  cmd   arg   arg    arg    arg    crc7  1
↑  ↑                                 ↑      ↑
起始 0  CMD 4 字节参数（高位在前）  7位CRC 停止位 1
```

举例：CMD17 读 LBA 1000

```
字节:   [0]    [1]    [2]    [3]    [4]    [5]
数值:   0x51   0x00   0x00   0x03   0xE8   0x??
       ↑CMD17  LBA[31:24]        LBA[15:8] LBA[7:0]  CRC
       (0x51 = 01010001,
        bit0=0 起始, bit1=1 方向(主机→卡), bit7~2 = 010100 = 0x14 = 22 = CMD17)

第 6 字节 = (CRC7 << 1) | 1，例如 CRC7 = 0b1001001 → 0x93
```

**起始位 + 停止位**：
- **每条命令的第 1 bit 永远是 0**（起始位）
- **最后 1 bit 永远是 1**（停止位）
- 中间 6 bit = 命令号 = `cmd & 0x3F`

例如 CMD17 (cmd=0x11)：
```
0  0  1  0  0  0  1  1   ← bit0 起始 0, bit7 停止 1, 中间 010001 = 0x11 = 17
   ↑               ↑
   起始位          停止位
```

### 2.4 响应格式（卡 → 主机）

- **R1**：1 字节，最高位固定 0，bit6~0 = 状态
  - 0x00 = no error（成功）
  - 0x01 = idle state
  - 0x04 = illegal command
  - 0x08 = CRC error
  - ...

- **R3 / R7**：5 字节 = 1 字节 R1 + 4 字节 OCR / echo data

### 2.5 数据块（read/write 时卡/主机发的 512 字节）

```
[0]   [1..512]    [513]  [514]
0xFE  512字节     CRC16  CRC16
↑             ↑    ↑      ↑
起始令牌       数据    CRC 高  CRC 低
0xFE = 读单块   0xFC = 写多块
0xFC = 写单块   0xFD = 多块停止
```

## 3. 逻辑分析仪怎么接

### 3.1 你需要的设备

- **逻辑分析仪**（任一支持 ≥ 25MHz 采样率的产品）：
  - Saleae Logic 8 / Logic Pro（最常见，100MHz+ 采样率）
  - sigrok 兼容的（淘宝 30 元的 CY7C68013A 也行）
  - 任何带 ≥ 3 个数字通道 + ≥ 25MHz 采样率的设备
- **探头夹**（logic analyzer 自带的那种细针夹，夹在板子上的引脚）

### 3.2 接线方法

```
         BT892XA2 板子
         ┌──────────────────────┐
PE5 (CMD) ├──┤         │   ← LA 通道 0（黄色线，CH0）
PE6 (CLK) ├──┤         │   ← LA 通道 1（橙色线，CH1）
PE7 (DAT0)├──┤         │   ← LA 通道 2（红色线，CH2）
         └──────────────────────┘

     逻辑分析仪
     ┌──────────┐
CH0 ─┤ 黄色探头 ├──
CH1 ─┤ 橙色探头 ├──
CH2 ─┤ 红色探头 ├──
GND ─┤ 黑色探头 /─ 接板子 GND（必须共地！）
     └──────────┘
```

**关键**：
- **GND 必须接板子 GND**（不然采样值会飘，全是噪声）
- 通道分配：CH0=CMD, CH1=CLK, CH2=DAT0

### 3.3 软件推荐 + 设置

#### 方案 A：Saleae Logic 2（最直观）

1. **新建项目** → 选择 Logic 2 设备
2. **通道设置**：
   - CH0 = "CMD" (黄色)
   - CH1 = "CLK" (橙色)  
   - CH2 = "DAT0" (红色)
3. **采样率**：100 MHz（够用）或 200 MHz（更精确）
4. **触发**：
   - 触发源选 CH1（CLK）
   - 触发方式：下降沿或电平
   - 因为 CLK 在 idle 时是低电平，主机开始发命令时第一个 bit 是 CLK 启动 → 用 **CH1 上升沿**触发
5. **采样长度**：50 M samples 起步（够抓到 1 条完整 CMD17 = 48 bits × 200MHz ≈ 50us，50M samples ≈ 250ms）

#### 方案 B：sigrok + PulseView（开源免费）

1. 打开 PulseView → 连接你的逻辑分析仪
2. **采样率**：100 MHz（sigrok 标识是 "100 MHz"）
3. **触发**：找 "CLK" 通道，Edge Rising
4. 抓完点右键 → "Export" 存成 `.csv`，可以用 Excel 看

#### 方案 C：手动分析（最基础）

如果你只有示波器（2 通道就够看 CLK + CMD），可以用示波器的 **Single trigger + Persistence 模式**抓一条命令的波形，然后用游标卡尺量 bit 宽度。

## 4. 怎么验证抓到的是"对的"

抓到一堆波形后，问自己 3 个问题：

### 4.1 时钟频率对不对？

在 `sd0_init` 期间（鉴定流程），SD 卡跑 **低速模式 ≈ 100~400 kHz**。在读写数据时跑 **高速模式 ≈ 24 MHz**。

测量 CLK：
```
低速：1 个 bit = 2.5~10 µs → 频率 100~400 kHz
高速：1 个 bit = 40 ns       → 频率 ≈ 24 MHz
```

如果 CLK 一直 0 → 卡的 SD 控制器没启动（`sd_gpio_init(0)` 没执行，或 `MUSIC_SDCARD_EN=0`）。
如果 CLK 一直高频 → 大概率是上次命令残留，正常。
如果 CLK 频率 ≈ 100 kHz 看到完整命令序列 → **低速模式正常**。

### 4.2 命令字节对不对？

把 CLK 上的脉冲**计数 + 在 CMD 上升沿采样**，找到 48 bit 命令。

举例：看到 CLK 上 48 个脉冲 + CMD 上的 6 个字节：

```
字节 1: 0101_0001  = 0x51 = CMD17  ✓
字节 2: 0000_0000  = 0x00  = LBA[31:24]
字节 3: 0000_0000  = 0x00  = LBA[23:16]
字节 4: 0000_0011  = 0x03  = LBA[15:8]
字节 5: 1110_1000  = 0xE8  = LBA[7:0]
字节 6: xxxx_xxx1  = CRC + 停止位
合计 LBA = 0x000003E8 = 1000 ✓
```

### 4.3 响应/数据字节对不对？

命令后过 2~8 个时钟周期，CMD 线上会有响应（卡驱动）。同样采样 8 bit 看字节。

如果是 R1 = 0x00 → 成功
如果是 0xFF → 通信错误

## 5. 我们 7 个测试任务的预期波形

### 5.1 Task 2: 鉴定流程（CMD0 → CMD8 → ACMD41 → CMD58 → ... → ACMD51）

**预期时长**：~50ms（低速模式）
**预期命令序列**：

```
t=0     CMD0    48 bits   卡响应 R1 = 0x01 (idle) 或 0x00 (ready)
t=2ms   CMD8    48 bits   卡响应 R7 = {0x01, 0x00, 0x00, 0x01, 0xAA}
t=4ms   CMD55   48 bits   卡响应 R1 = 0x01 (idle)
t=4ms   ACMD41  48 bits   卡响应 R3 = {R1, OCR[4 bytes]}
        ↓ 循环 ACMD41 直到 OCR[31]=1 (~30ms)
t=34ms  CMD58   48 bits   卡响应 R3 = {R1, OCR}
t=36ms  CMD2    48 bits   卡响应 R2 = {CID 16 字节}  ← 注意：CMD2 响应是 136 bit
t=38ms  CMD3    48 bits   卡响应 R6 = {R1, RCA[4 字节]}
t=40ms  CMD9    48 bits   卡响应 R2 = {CSD 16 字节}
t=42ms  CMD7    48 bits   卡响应 R1 = 0x00 (进入 tran)
t=44ms  CMD55   48 bits   卡响应 R1 = 0x00
t=44ms  ACMD51  48 bits   卡响应 R1 + 8 字节 SCR data
t=50ms 鉴定完成
```

**逻辑分析仪看什么**：

1. **看到 ~7 条命令**（每条 48 bit = 48 个 CLK 脉冲）
2. **第一条是 CMD0**：第一个字节 = 0x40（`0 1 0 0 0 0 0 0`，CMD0 = 0）
3. **最后一条是 ACMD51**：第一个字节 = 0x7A
4. **相邻命令间有几个空闲时钟周期**（idle time）

**完整命令字节表（你可以照着核对）**：

| 命令 | 字节 1 (命令号) | 字节 2-5 (参数) | 字节 6 (CRC7+stop) |
|---|---|---|---|
| CMD0 | 0x40 | 0x00 0x00 0x00 0x00 | 0x95 |
| CMD8 | 0x48 | 0x00 0x00 0x01 0xAA | 0x87 |
| CMD55 | 0x77 | 0x00 0x00 0x00 0x00 | 0x65 |
| ACMD41 | 0x69 | 0x40 0x00 0x00 0x00 | 0x77 |
| CMD58 | 0x7A | 0x00 0x00 0x00 0x00 | 0x00 |
| CMD2 | 0x42 | 0x00 0x00 0x00 0x00 | 0xAF |
| CMD3 | 0x43 | 0x00 0x00 0x00 0x00 | 0x6F |
| CMD9 | 0x49 | 0x00 0x00 0x00 0x00 | 0x00 |
| CMD7 | 0x47 | RCA 0x00 0x00 0x00 | xxxx |
| ACMD51 | 0x73 | 0x00 0x00 0x00 0x00 | xxxx |

> **怎么记命令字节**：CMD 号 = 第 1 字节的 bit7~2。`cmd_byte = (cmd_number << 2) | 0x40`。例 CMD0: `0 << 2 | 0x40 = 0x40`；CMD17: `0x11 << 2 | 0x40 = 0x44 | 0x40 = ...` 等等。

### 5.2 Task 3: 单块读（CMD17）

**预期时长**：1~2 ms（高速模式 24 MHz）
**命令序列**：

```
主机 → CMD17 (48 bits: 0x51 0x00 0x00 0x03 0xE8 CRC)
        ↓ 2~8 个时钟周期
卡 →   R1 (8 bits: 0x00)
        ↓ 几个时钟周期（卡准备数据）
卡 →   Start Token (8 bits: 0xFE)
        ↓
卡 →   512 字节数据 + 2 字节 CRC16
        ↓ 传输期间 DAT0 由卡驱动
主机 ← 收完 512 字节后不再管 DAT0
```

**逻辑分析仪看什么**：

1. **CMD17 命令字节**：`0x51 0x00 0x00 0x03 0xE8 [CRC+1]`
2. **R1 响应字节**：CMD 线在收到响应后变低电平采样，应该是 `0b00000000 = 0x00`
3. **0xFE 起始令牌**：DAT0 线拉低后第一个字节 = 0xFE
4. **512 字节数据**：DAT0 上连续的字节流，第一个字节应该是 0xE8（如果 LBA 1000 是上一轮 Task 6 写的）或 0x00（如果是空）
5. **2 字节 CRC16**：最后 2 个字节（不用解码，知道存在即可）

**我们测出的 16 个字节**：`E8 E9 EA EB EC ED EE EF F0 F1 F2 F3 F4 F5 F6 F7`
- LBA 1000 = 0x03E8，所以每个字节 = `(0x03E8 + i) & 0xFF`：
  - i=0: 0xE8 ✓
  - i=1: 0xE9 ✓
  - i=2: 0xEA ✓
  - ... i=15: 0xF7 ✓

**完全对得上 Task 6 写入的 pattern**！

### 5.3 Task 5: 单块写（CMD24）

**预期时长**：5~15 ms（高速模式 + NAND 编程）
**命令序列**：

```
主机 → CMD24 (48 bits: 0x58 0x00 0x00 0x03 0xE8 [CRC+1])
        ↓
卡 →   R1 (0x00)
        ↓ 至少 1 个时钟周期
主机 → Start Token 0xFE (主机驱动 CMD 线)
        ↓
主机 → 512 字节数据 (主机驱动 DAT0 线)
        ↓
主机 → 2 字节 CRC16 (主机驱动)
        ↓
卡 →   1 字节 status response (0x05 表示接受 / 0x0D 表示 CRC 错)
        ↓
卡 →   DAT0 拉低表示"busy" (约 1~10 ms，NAND 编程)
        ↓
卡 →   DAT0 拉高表示编程完成
```

**逻辑分析仪看什么**：

1. **CMD24 命令字节**：`0x58 0x00 0x00 0x03 0xE8 [CRC+1]`
2. **R1 响应**：`0x00`
3. **0xFE 令牌**：CMD 线上（注意：写命令的令牌是在 **CMD** 线，不是 DAT0！）
4. **512 字节数据**：DAT0 线上，第一个字节是 0xE8（pattern 第一个字节）
5. **1 字节 status**：DAT0 线上，应该是 0x05（低 5 bit = xxx00101 = 接受；高 3 bit = 0）
6. **忙信号**：status byte 之后，DAT0 拉低持续几 ms，然后拉高

**关键区别**：CMD24 的 0xFE 令牌是在 **CMD 线** 上（不是 DAT0）；CMD17 没有令牌。

### 5.4 Task 4/6/7 的多块命令（CMD18/CMD25）

我们 SDK 没暴露多块 API，所以是循环单块（CMD17 / CMD24）。每个块之间：

```
[CMD17 单块][1ms 间隔][CMD17 单块][1ms 间隔]...[CMD17 单块]
```

每次都是独立的"命令-响应-数据"序列。逻辑分析仪看到的是 **N 次 CMD17** 而不是 1 次 CMD18 + CMD12。

但好消息：**调试和分析更简单**——每条命令独立，没有跨块的令牌管理。

## 6. 怎么手动解码 1 条命令（示例）

假设你在 CH1 (CLK) 上看到 48 个脉冲，在 CH0 (CMD) 上看到 6 个字节的位流：

### 6.1 数 CLK 脉冲，分组

```
CLK: ──┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ... 48 个脉冲 ... ┌─┐
      └─┘ └─┘ └─┘ └─┘ └─┘                └─┘
       \_____________/\_____________/.../____/
         字节 1 (8 bit)  字节 2 (8 bit)   字节 6
```

### 6.2 每个字节：MSB 在前

假设第 1 个字节 8 个 CLK 周期内 CMD 线的电平：

```
时刻     1   2   3   4   5   6   7   8
CMD电平  0   1   0   1   0   0   0   1
       MSB                           LSB
       ↓                             ↓
二进制: 01010001 = 0x51
```

**CMD 号 = (byte1 >> 2) & 0x3F** = `(0x51 >> 2) & 0x3F` = `0x14` = 20... wait

CMD17 的 cmd 号 = 17 = 0x11
`cmd_byte = (0x11 << 2) | 0x40` = `0x44 | 0x40` = `0x44`? No that's wrong.

让我重新算：`cmd_byte = cmd_no << 2 | 0x40` (host→card) or `cmd_byte = cmd_no << 2` (card→host for response).

CMD17 (cmd=0x11):
- `0x11 << 2 = 0x44`
- `0x44 | 0x40 = 0x44`  (因为 0x44 已经有 bit6=1)
- wait: `0x44 = 0100 0100`, bit6 = 1, 所以 | 0x40 不变 = 0x44

Hmm let me re-check. The cmd byte format is:
- bit 7 = 0 (start bit)
- bit 6 = 1 (host→card direction) **OR** 0 (card→host)
- bit 5..0 = command number (6 bits)

So:
- CMD0: cmd_byte = `0 | 0 | 000000` = `0x40` ✓
- CMD17 (0x11): cmd_byte = `0 | 1 | 010001` = `0x51` ✓

So cmd_byte = `(0 << 7) | (1 << 6) | (cmd_no & 0x3F)` = `(cmd_no & 0x3F) | 0x40` for host→card.

Let me re-verify:
- CMD0 = 0x00: `0 | 0x40 | 0x00` = `0x40` ✓
- CMD17 = 0x11: `0 | 0x40 | 0x11` = `0x51` ✓
- CMD24 = 0x18: `0 | 0x40 | 0x18` = `0x58` ✓
- CMD55 = 0x37: `0 | 0x40 | 0x37` = `0x77` ✓
- ACMD41 = 0x29: `0 | 0x40 | 0x29` = `0x69` ✓

OK so the formula is `cmd_byte = 0x40 | cmd_no` for host→card.

For card→host responses (like R1), the start bit is still 0 and the direction bit is 0:
- R1 success = `0x00` (all zero = "no error")
- R1 idle = `0x01`

### 6.3 计算参数（LBA）

第 2-5 字节是参数（大端）。LBA 1000 = `0x000003E8`：
- 字节 2: `0x00`
- 字节 3: `0x00`
- 字节 4: `0x03`
- 字节 5: `0xE8`

所以 CMD17 的完整 6 字节 = `0x51 0x00 0x00 0x03 0xE8 CRC+1`

### 6.4 校验 CRC

CRC7 是循环冗余校验，公式：
```
CRC7 = x^7 + x^3 + 1
```

你可以用网上的 CRC7 计算器：
- 输入：`0x51 0x00 0x00 0x03 0xE8 0x00`（最后 1 字节填 0）
- 多项式：`0x09` (x^7 + x^3 + 1)
- 输出：应该是某个值，左移 1 位 + 1 = 字节 6

实际 SDK 用硬件 CRC7 计算，如果协议实现正确，第 6 字节一定对得上。

## 7. 常见问题排查

### 7.1 抓不到任何波形

| 可能原因 | 检查 |
|---|---|
| 探头接错 | 检查 CH0/CH1/CH2 是否对应 PE5/PE6/PE7 |
| GND 没接 | 用万用表量 LA 的 GND 和板子 GND，应该通 |
| 触发设置错误 | 试试改"立即触发"，看有没有任何边沿 |
| 卡没插 / 卡供电没接 | 板子上电后卡座应该亮（如果有指示灯） |

### 7.2 抓到的 CMD 字节对不上

| 可能原因 | 检查 |
|---|---|
| MSB/LSB 颠倒 | 重新确认你按 MSB 在前解码（SD 卡是 MSB-first） |
| bit 顺序记错 | 起始 bit 永远是 0；中间 6 bit 是命令号；最后 1 bit 是 1 |
| 信号被干扰 | SDCLK 走线太长 / 没加 10k 上拉 |

### 7.3 看到波形但 CRC 校验不过

| 可能原因 | 检查 |
|---|---|
| 采样率太低 | 提高到 100MHz+ |
| 时钟边缘采样错误 | Saleae 协议解码器有时会"看错"边沿，**用 raw 波形手动解码**最准 |
| 卡是便宜的非标卡 | 已知有些廉价卡在某些命令上不严格校验 CRC（init 流程尤其宽容） |

### 7.4 想看 0xFE 起始令牌但找不到

写命令的 0xFE 在 **CMD 线**上（不是 DAT0）。如果你只盯着 DAT0，会以为"没有令牌"。

### 7.5 数据全是 0xFF

可能是：
- 卡没初始化成功（CMD17 失败 → 卡不送数据 → DAT0 一直空闲高电平 = 0xFF）
- 你的探头接到 DAT3 或 DAT1（未用的数据线空闲时是高电平）

### 7.6 LA 探头不够用时的两段式调试

**实际场景**：你的开发板 / 杜邦线数量有限，**没法同时接 TF 卡 + LA 探头**（需要 PE5/PE6/PE7 + GND 共 4 根 LA 探头，加上 TF 卡本身的 6+ 根接线）。

**解决方案 — 两段式验证**：

**阶段 1：LA 验证主机协议**（断开 TF 卡）

1. 把 TF 卡的 VDD/CMD/CLK/DAT0/GND 等杜邦线**全部断开**
2. LA 探头接 BT892XA2 的 PE5/PE6/PE7 + GND
3. 启动芯片，触发抓取
4. 你会看到 SDK **仍然发出完整命令序列**（CMD0 → CMD8 → CMD55 → CMD0 → ...），因为主机不知道卡没接，照常发送
5. 用 LA 协议解析器（如 Kingst VIS 的 SDIO Analyzer）解码：
   - 命令字节是否符合预期？
   - CRC7 是否正确？
   - 时钟频率是否正确？
6. **此时 `sd0_init` 会 FAIL**（正常反应，因为没卡响应）

**阶段 2：功能测试**（断开 LA，接回 TF 卡）

1. 断开 LA 探头
2. 把 TF 卡的接线恢复
3. 启动芯片，看串口 `sd0_init OK` + 各 Task PASS

**两段式组合 = 端到端验证**：
- 阶段 1 证明：**协议字节 / CRC / 时序**正确（物理层 OK）
- 阶段 2 证明：**SDK 逻辑 / 卡响应**正确（链路层 OK）

**实测案例**：本指南用户用 Kingst VIS LA1010 + 4 根杜邦线验证，阶段 1 抓到：
```
CMD0 GO_IDLE_STATE  ARG: 0x00000000  CRC: 0x4A  ✓
CMD8 SEND_IF_COND   ARG: 0x000001AA  CRC: 0x43  ✓
CMD55 APP_CMD       ARG: 0x00000000  CRC: 0x32  ✓
```
三个 CRC 跟文档预期完全一致，证明协议实现正确。

**注意**：Kingst VIS 的 SDIO Analyzer 有个小 bug——会把 ACMD41（cmd byte = `0xE4`）错误识别为 CMD1（cmd byte = `0x44`）并标记为 "Unknown"。这是解析器的问题，不是协议问题。ACMD41 的 arg 是 `0x40FF8000`（HCS=1 + OCR 任意电压），如果看到 arg = `0x40FF8000` + 解析器说 "CMD1 Unknown"，实际就是 ACMD41。

## 8. 实战：用 Saleae Logic 2 解码

### 8.1 打开协议分析器

1. 抓完一段波形后，点"Analyzers" 标签
2. 添加 "SPI" 解码器（**SD 协议没有专用解码器，但 SD 模式在物理层类似 SPI**）
   - **不过 SD 是全双工 + 独立命令线**，SPI 解码器不能完全适配
3. **实际推荐**：手动分析（用 §6 的方法），或者用 Saleae 的 "Async Serial" 解码器配 CMD 线（虽然不是 SD 协议，但能看到字节流）

### 8.2 推荐工具链

| 工具 | 用途 |
|---|---|
| **Saleae Logic 2** | 抓波形，导出 CSV |
| **sigrok/PulseView** | 开源免费，有 SD 卡的"近似"解码器 |
| **Excel + 手动脚本** | 导出 CSV 后写脚本解析字节流 |
| **Python + bitstring 库** | 自动化分析大量抓取数据 |

### 8.3 推荐的 Python 脚本框架（如果想批量分析）

```python
from bitstring import BitStream

# 从 Saleae 导出的 CSV 读 CLK 和 CMD
samples = read_csv('capture.csv')

# 找 CLK 上升沿
clk_edges = find_rising_edges(samples['CLK'])

# 在每个 CLK 上升沿采样 CMD
bits = [sample_cmd_at(clk_edge, samples['CMD']) for clk_edge in clk_edges]

# 把 bit 流分组为字节（MSB first）
bytes_data = []
for i in range(0, len(bits), 8):
    byte_bits = bits[i:i+8]
    byte_val = int(''.join(str(b) for b in byte_bits), 2)
    bytes_data.append(byte_val)

# 解码命令
if bytes_data[0] in CMD_TABLE:
    cmd = CMD_TABLE[bytes_data[0]]
    print(f"Command: {cmd['name']}, args: {bytes_data[1:5]}")
```
