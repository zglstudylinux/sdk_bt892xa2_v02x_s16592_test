## 1. 构建产物映射表

### 1.1 一行管

> 整个 `Output/` 树是 **obj**（.o 文件）+ **bin**（.dcf 等） + **lst**（map.txt 等）的组合。**全是工具链中段产物**，按时间戳看 Build 是不是成功了。

| 文件 | 由谁 | 内容 | 被谁消费 | 能否删除？ |
|---|---|---|---|---|
| `Output/obj/<...>.o` | `riscv32-elf-gcc -c` | 单文件未链接（机器码） | 链接器 | 删了下次 Build 重编，影响不大 |
| `Output/lst/<...>.lst` | `--listing` 模式 | 汇编/asm list | debug、阅读 | 删了不重生成，没影响 |
| **`Output/bin/app.bin`** | `riscv32-elf-objcopy -O binary` | 纯二进制 img | DCF 打包 | ❌ 是结果 |
| **`Output/bin/app.dcf`** | `xmaker` 包装 | **DCF 容器**：header + flash img + xcfg + updater + 签名 | **Downloader.exe** 烧入 | ❌ 是结果 |
| `Output/bin/app.rv32` | `riscv32-elf-gcc` 默认输出 | ELF（带符号） | `objdump / nm / gdb` | 调试用，删了 build 重连接再生成 |
| `Output/bin/app.hex` | 偶尔转换 | Intel HEX（烧录） | 老款烧录器 | 不需要，默认不生成 |
| **`Output/bin/map.txt`** | `-Wl,-Map=...` | 链接报告：每个函数在哪个 addr、占多大 | debug | 调试用，删了下次自动重建 |
| `Output/bin/Settings/Boombox.setting` | xmaker 步骤 | GUI 工具用的 UI 配置（哪些键、显示模式）| Downloader 加载 | ❌ 双击 edit |
| `Output/bin/xcfg.bin` | xmaker 步骤 | 运行时参数（二进制） | 启动时 `xcfg_init()` 读 | ❌ |
| `Output/bin/xcfg.c` | xmaker 反向 | xcfg 的 C 形式定义（给程序看）| 编译时 | 删了 build 重生成 |

### 1.2 关键理解

```
编译一次
│
├── 把 .c + .S 文件各编成 .o
├── 把所有 .o 链成 .rv32（ELF）
├── 再 objcopy 提取出 .bin
├── 再 objdump -d 反汇编给 lst
├── xmaker 把 .bin + xcfg.bin + updater + 签名打包成 .dcf
│
总产物：
  app.dcf (720 KB)    ← 烧录用
  app.bin (700 KB)    ← raw img，debug 看 hex dump
  app.rv32 (900 KB)   ← ELF，debug 看符号
  map.txt (200 KB)    ← 链接器报告
  xcfg.bin (256 B)    ← 运行时配置
```

### 1.3 为什么不是单一 `Makefile`

SDK **没有 Makefile**，原因：

1. **二进制库（`.a`）**：链接时要拼一个清单，和 Makefile 重生成冲突
2. **多 profile**：同一个工程可能 build 给 Boombox / 蓝牙耳机 / 充电宝，三个产品用不同 xcfg.xm
3. **自动下载钩子**：xmaker 可以集成"build 完自动调 Downloader 烧入"，Makefile 难以表达
4. **依赖 CB 时间戳**：CB UI 会自动重生成链接参数

替代品是 Code::Blocks 的 `app.cbp` (project file, XML) + xmaker 的 `.xm` (DSL)。

### 1.4 第一次 Build 会多久

| 项目 | 首次 (cold) | 增量 |
|---|---|---|
| 空 `app` 工程（hello_world） | ~30 秒 | ~1 秒 |
| 加 wav_test (Phase 5) | ~50 秒 | ~2 秒 |
| 完整 SDK 工程 | ~3 分钟 | ~10 秒 |

冷编译时间**大部分**花在编译 `libvoices.a / libcodecs.a / libbtstack.a`——这些你**不能用 CB 手改动它们**。

## 2. Code::Blocks "Add files" 实际操作

### 2.1 为何要手动

CB 不会自动扫描文件夹中所有 `.c` 文件。

> 这是 CB 老版本历史包袱，新工程**第一次打开时**你需要手动把每个 `.c` 加进来。

### 2.2 ASCII 截图

#### 步骤 1：打开 project 右键菜单

```
Project tab
├─ app/
│  ├─ app/
│  │  ├─ main.c
│  │  ├─ wav_test/
│  │  │  ├─ wav_test.c          ← 你新的文件
│  │  │  └─ wav_test.h
│  │  └─ ... 
│  └─ ...

右键点击 'wav_test/' 文件夹  (注意是文件夹不是文件)
└─ Add files recursively...
```

#### 步骤 2：选择文件

会跳出"Add files to project"窗口。**关键陷阱**：

| 操作 | 效果 |
|---|---|
| Add files | 单文件选择 |
| **Add files recursively** | 把文件夹 + 所有子文件夹全加 |
| Add directory | **不！** 这个是加 unit 名（fp），不是把 .c 加进工程 |

#### 步骤 3：检查 `.cbp`

加完后，`.cbp` 文件底部应该新增 `<Unit filename="...wav_test.c">`。

> 这一步如果只看到 `<Add directory="..."/>` 但没有 `<Unit filename>`，**说明你点错了 Add 命令**——你的文件**还没进 build**。

### 2.3 验证加入成功

Build log 应该出现：

```
Compiling: wav_test.c
```

没出现就是没加上。

### 2.4 `<Unit>` 的精确结构

```xml
<!-- .cbp 里的某行 -->
<Unit filename="app/projects/standard/wav_test/wav_test.c">
    <Option compilerVar="CC" />
    <Option compile="1" />
    <Option linked="1" />
</Unit>
```

| 字段 | 含义 |
|---|---|
| `filename` | 相对路径（相对 .cbp 所在目录） |
| `compilerVar="CC"` | 用 C compiler（ASM 用 `CC` 也是同样，不一定叫 ASM）|
| `compile="1"` | 编译它 |
| `linked="1"` | 链入最终 ELF |

如果 `compile="0"` → 文件不会编译，只是为了 IDE 跳过去用。
如果 `linked="0"` → 编译但不连进最终 ELF（debug-only 模式不常用）。

## 3. Compiler profile 深挖：`riscv32`

### 3.1 Profile 的本质

CB 把所有"编译参数"藏进一个 named profile。**项目级**和**全局**两层都有：

| 层 | 在哪 | 谁改 |
|---|---|---|
| **全局 profile** | Settings → Compiler → Selected compiler | 工具装好时配置，**几乎不动** |
| **项目 profile** | Project → Build options | 项目级覆盖，如 `-DPHASE_5=1` |

### 3.2 全局 profile 检查清单

打开 Settings → Compiler → 选 `GNU GCC Compiler for RISC-V (riscv32)`：

| Tab | 该看什么 |
|---|---|
| **Compiler settings / General** | `#defines` 应有 `__riscv 1` 之类 |
| **Toolchain executables** | `Compiler's installation directory` 是 `riscv32-elf-gcc.exe` 所在目录 |
| | `C compiler` 是 `riscv32-elf-gcc.exe` |
| | `C++ compiler` 是 `riscv32-elf-g++.exe`（可不用，但 CB 会查） |
| | `Make` 是 `make.exe`（CB 默认调 GNU make）|

### 3.3 验证工具链能独立跑

PowerShell：

```powershell
where.exe riscv32-elf-gcc
# → 显示 <安装路径>/bin/riscv32-elf-gcc.exe

riscv32-elf-gcc --version
# → GNU ... RISC-V ... 版本信息
```

如果 `where` 找不到：

1. **路径没加 PATH**：手动加 `C:\path\to\riscv32\bin` 到环境变量
2. **profile 配错**：Profile 的 dir 是另一处
3. **工具链没装**：问同事要安装包

### 3.4 多 profile 共存的现状

工程可能有 2 个 profile：

| Profile | 目标 | 链什么 |
|---|---|---|
| `GNU GCC Compiler for RISC-V (riscv32)` | RISC-V 32-bit | 默认 |
| 其它（如 `GNU GCC Compiler for RISC-V (riscv64)`）| 64-bit | 不常用 |

切换：顶部 **Selected compiler** 下拉。

> 注意：BT892XA2 是 **32-bit RISC-V**——选错会得到编译失败。

## 4. xmaker 深挖：`.xm` 是什么

### 4.1 是什么

`.xm` 是 SDK 自家 DSL（类 C），由 `xmaker.exe` 解释执行。它生成：
- `xcfg.bin`（256 B 二进制）
- `Settings/Boombox.setting`（下载工具 UI 配置）
- 还会编排 `prebuild.bat` / `postbuild.bat`

### 4.2 一个典型 `.xm`（简化版）

```
// xcfg.xm  - snippets from real project
xm_set(ProjectName, "BT892XA2 Standard");
xm_set(BinName, "app");

#if PWRKEY_TEST_MODE
    xm_set(BomKey, "boombox_pwrkey.setting");   // 选 PWRKEY 板配置
#else
    xm_set(BomKey, "boombox.setting");
#endif

depend("xcfg.bin");                             // 依赖，确保 rebuild
setflash();                                     // 设下载模式
make();                                         // 跑 GVmaker
save();                                         // 写出 Settings
```

### 4.3 xmaker 的"五个关键命令"

| 命令 | 干啥 |
|---|---|
| `depend(...)` | 声明文件依赖列表，xmaker 知道啥改了得重 build |
| `setflash(...)` | 设烧录模式（XIP / demo / config 等）|
| `make(...)` | 跑 GVmaker / prebuild.bat |
| `save()` | 把 `Settings/Bomkey.setting` 写出 + 触发 postbuild.bat |
| `xm_set(...)` | 自定义 key=value，给 Make 读 |

### 4.4 prebuild.bat / postbuild.bat 调用链

CB 不知 `.xm`，靠 `prebuild.bat` / `postbuild.bat` 把生命周期交到 `.xm` 手里：

```
点击 'Build'
    ↓
CB 调 'prebuild.bat'        ← 1. 干点热身：清理上次 .o 之类
    ↓
CB 调 'riscv32-elf-gcc -c'  ← 2. 编译每个 .c 到 .o
    ↓
CB 调 linker                ← 3. 链接 .o 到 .rv32
    ↓
CB 调 'postbuild.bat'       ← 4. objcopy 出 .bin + xmaker 出 .dcf
    ↓
Build 完成
```

**典型 postbuild.bat 简化**：

```bat
@echo off
riscv32-elf-objcopy -O binary app.rv32 app.bin
cd /d "%1"
copy app.bin "..\..\Output\bin\app.bin"
"%XMAKER%" ..\..\xcfg.xm
```

`%XMAKER%` 是 SDK 安装目录里的 `xmaker.exe`。

### 4.5 手跑 xmaker

```powershell
cd D:\work\sdk_bt892xa2_v02x_s16592_20251212\app\projects\standard\
$env:XMAKER = "C:\path\to\xmaker.exe"
.\xcfg.xm         # 实际写法由 SDK 定，能手跑
```

如果你搞不定，**别折腾**——CB 已经把这些都做了，你只需要 GUI。

## 5. DCF 容器格式

### 5.1 是什么

`.dcf` 是**BT892XA2 自有容器**，把"烧录文件需要的所有东西"打包到一个文件：

```
┌──────────────────────────────────────────────┐
│  Header (16 B)                                │
│    "DCF\0\0\0\0\0\0\0\0" magic                │
│    version, board id, flags...                 │
├──────────────────────────────────────────────┤
│  App Region (变长)                             │
│    flash app.bin                               │
├──────────────────────────────────────────────┤
│  Resource Region (变长)                        │
│    .wav_buf 区 + 字符串 + 表                   │
├──────────────────────────────────────────────┤
│  XCFG Region (256 B)                           │
│    xcfg.bin 拷入                              │
├──────────────────────────────────────────────┤
│  Updater Region (变长)                          │
│    OTA 升级用，可选                            │
├──────────────────────────────────────────────┤
│  Signature (16 B)                              │
│    CRC / signature                             │
└──────────────────────────────────────────────┘
```

### 5.2 自验证 DCF

PowerShell：

```powershell
$bytes = [System.IO.File]::ReadAllBytes("Output\bin\app.dcf")
"first 16 bytes:"
[BitConverter]::ToString($bytes[0..15])
# 应输出 DCF magic + 一些 reserved

"length:"
$bytes.Length
# 720 KB 左右
```

或 hex 编辑器（Visual Studio Code + Hex Viewer 插件）：

```
Offset  Content
0x00    44 43 46 00  (DCF\0)
0x04    00 00 ...
0x10    ...
```

### 5.3 解包工具（如果有）

SDK 提供 `dcf_tool.exe`（个别 SDK 才有）能解回 `.bin / xcfg.bin`，没的话 hex 翻。

## 6. Downloader GUI 操作

### 6.1 是什么

`Downloader.exe` 是把 `.dcf` 烧到板子的 GUI。流程：

```
Open .dcf 文件
↓ 改 xcfg 任意项目（运行时配置）
↓ 选 COM 端口
↓ 选下载模式：可能是 'download 模式' / 'upgrade 模式'
↓ 按下 'Download'
↓
Progress bar 0% → 100%
↓
完成：板子自动重启
```

### 6.2 BOOT 进入下载模式

**这一步工具不替我们做**——靠硬件：

- 大多数 BT 板都有**一个按钮叫 BOOT** 或 BOOT-PAD
- 操作：按住 BOOT → 按 RESET → 灯变红/绿 = 进入 download mode
- 也可以用 **GPAD 转 TTL** 控制 reset (拉低 reset 100ms)
- 有时还要选 **具体下载口**（UART-I / UART-II）

### 6.3 GUI 步骤（典型）

```
[1] Open File (Ctrl+O)
    → 选 .dcf (app/projects/standard/Output/bin/app.dcf)

[2] 修改 xcfg (控件区)
    → user_pwrkey_en 翻成 True
    → KEY 配置 (KU_PLAY/KU_NEXT/KU_PREV)
    → LED 配置

[3] 选择 COM (右上角)
    → 看设备管理器里 USB-TTL 在 COM?
    → 波特率（不是 HUART 那个，是 Downloader 的）

[4] 烧录
    → Start / Write
    → 进度条
    → 看 console 区打 log

[5] 完成
    → 板子自动重启
    → 串口可开 HUART 看 banner
```

### 6.4 常见错误

| 错 | 原因 |
|---|---|
| 找不到串口 | USB-TTL 没插 / 驱动没装 / 端口被占用 |
| 进不了 download mode | BOOT 键没按住/RESET 顺序错 |
| 烧录失败 CRC | .dcf 文件损坏，重新构建 |
| 自动重启后没声音 | xcfg 配置错了 |
| 烧一半 60% 卡死 | boot mode 提前掉电 |

## 7. Shell 等价命令

### 7.1 为什么要懂这个

- **GUI 出 bug**：CB 偶尔找不到 profile / 错位，自己手命令行 build
- **批量构建**：CI 自动 build
- **debug 编译问题**：CB 报"unresolved reference"是链接错，要看具体哪个 obj 没链进去

### 7.2 单文件编译

CB GUI 一次 Build 实际做的事（PowerShell）：

```powershell
cd D:\work\sdk_bt892xa2_v02x_s16592_20251212\app\projects\standard\

# 1. 编译每个 .c -> .o
riscv32-elf-gcc `
    -c `
    -I include -I app -I platform/header `
    -I fat_test -I wav_test `
    -DUSER_PWRKEY=1 `
    -O2 -g `
    -ffunction-sections -fdata-sections `
    -march=rv32imacxbs1 -mabi=ilp32 `
    -Wall `
    -o Output/obj/wav_test/wav_test.o `
    wav_test/wav_test.c
```

### 7.3 链接所有 .o -> ELF

```powershell
riscv32-elf-gcc `
    -nostdlib `
    -Wl,--gc-sections `
    -Wl,-Map=Output/bin/map.txt `
    -Tapp/projects/standard/ram.ld `
    -o Output/bin/app.rv32 `
    Output/obj/main.o Output/obj/wav_test/*.o ... `
    ...lib*.a...
```

### 7.4 ELF → BIN

```powershell
riscv32-elf-objcopy -O binary Output/bin/app.rv32 Output/bin/app.bin
```

### 7.5 典型 step 总结

| GUI 动作 | shell 等价 |
|---|---|
| `Ctrl+F9` Build | 上 5.1 + 5.3 + 5.4 + postbuild.bat 全套 |
| 单文件"Compile current file" | `riscv32-elf-gcc -c your.c -o your.o` |
| "Rebuild"（重生成链接） | `rm Output/obj/*; Ctrl+F9` |

> ⚠️ 实际上 CB 还要处理：include search path、defines、include libs、链接顺序、xmaker 调用……**手命令行就只用来调单一错误**。

## 8. HUART 调试串口

### 8.1 三个旋钮

| 旋钮 | 配置 | 影响 |
|---|---|---|
| `HUART_EN` | 0/1 | 0 = 关闭 UART 块，1 = 启 |
| `HUART_SEL` | IO_PA7/IO_PB3/... | 选哪个 IO 脚 |
| `UART0_PRINTF_SEL` | 0/1/... | printf 走哪个 UART |

### 8.2 config.h 默认

```c
// config.h
#define HUART_EN             1       // 1 = 启
#define HUART_SEL            IO_PB3  // 你板子是 PB3
#define UART0_PRINTF_SEL     0       // printf 走 uart0
```

### 8.3 配置变化影响

| 谁设 | 怎么改 |
|---|---|
| 想换到 PA7 | `HUART_SEL = IO_PA7` + PCB 走线 |
| 想让另一个 UART 能 printf | `UART0_PRINTF_SEL = 0` (HUART), `=1` (其他) |
| 想关 HUART 调试 | `HUART_EN = 0`（少 5KB 代码体积） |

### 8.4 自动互斥逻辑

`config_extra.h:723-781`（别动！）有"if HUART_SEL = PB3，会自动让那个 IO 切到 UART"——避免你跑了 HUART 但 PB3 还在被 GPIO 占用。

> 这部分逻辑复杂，**新手阶段不要改**，直接用默认。

### 8.5 build 一致性验证

```
Build log 应有：
  Compiling: bsp_uart.c
  Linking app.rv32
  + xmaker 相关 log
```

如果 `bsp_uart.o` 没出现，说明 `HUART_EN=0` 关了，printf 会**静默失败**（编译器不提示）。

## 9. 构建失败 FAQ（10 条）

> 💡 **这一节的位置最关键**：第一次 Build 失败时，先翻这 10 条；如果你的错不在此，再去 [06 §1 工具链 8 坑](06_踩坑大全.md)。

### 9.1 "riscv32-elf-gcc: not found"

```
Fix:
  1. 工具链没装 —— 问同事
  2. PATH 没加 —— 系统属性 → 高级 → 环境变量 → PATH 加 bin 目录
  3. CB Profile 路径错 —— Settings → Compiler → Toolchain 检查
```

### 9.2 "Cannot find include.h"

```
Fix:
  include path 没加。
  CB: Project → Build options → Search directories → Add 想扫的目录
  通常已经设好，问题在：你的 .cbp 用了绝对路径，搬代码后失效
```

### 9.3 "postbuild.bat failed, exit code 1"

```
Fix:
  1. 调出 cmd，cd 到项目目录，手跑 postbuild.bat，看具体啥错
  2. 经常是 xmaker.exe 找不到 —— %XMAKER% 环境变量没设
  3. 或 Boombox.setting 写得不对 (.xm 错)
```

### 9.4 "undefined reference to pff_open" 之类

```
Fix:
  1. pff.c 没加到工程 —— 看 .cbp 是否包含 `fat_test/pff.c`
  2. 编译器宏冲突 —— 打开 api_fs.h 看 FRESULT 定义
  3. 链接顺序 —— pff.o 要比 lib*.a 早连
  → 详 [05 §6](05_PetitFatFs源码导读.md)
```

### 9.5 "region 'ram' overflowed by X bytes"

```
Fix:
  BSS 超限。
  1. 检查是否 static array 开太大
  2. 移到 aram section
  3. 链接脚本改 ram.ld (新手不要改)
  → 详 [02 §1.3](02_BT892XA2芯片与外设地图.md)
```

### 9.6 "xcfg.bin invalid length, expected 256 got X"

```
Fix:
  1. xmaker.exe 出错 —— 重 build
  2. .xm 改过忘了重 build
```

### 9.7 "DCF header magic error"

```
Fix:
  1. objcopy 没出 .bin 干净 —— 删 Output 重新 build
  2. .dcf 是半写的 —— 重烧完整 .dcf
```

### 9.8 "map.txt 没有 my_func"

```
Fix:
  1. 函数被 -ffunction-sections 切走了 —— 加 __attribute__((used)) 或 __attribute__((section(".text")))
  2. 函数没编译进 —— 查 .cbp
  3. 函数被 -Wl,--gc-sections 切了 —— 加 KEEP(*(.text.my_func))
```

### 9.9 Build 成功后烧不进

```
Fix:
  1. .dcf 是上一次的产物 —— 看 Output/bin 的 mtime
  2. 下载模式没进 —— 复 §6.2 BOOT
  3. 串口线接错 —— TX/RX 交叉？GND 共？
```

### 9.10 编译时 static_assert / 语法检查失败

```
Fix:
  1. 几乎总是 SDK macro.h 没 include —— 顶部加 #include "macro.h"
  2. SDK 头文件版本问题 —— 看 sdk_version.c / config_extra.h
```

### 9.11 + 1 个 bonus — "中文 print 在串口乱码"

```
Fix:
  串口工具编码选 UTF-8，不要 GBK。
  XCOM 字符编码设置。
```

## 总结：核心清单

读完本篇后，**最少要保证**：

- [ ] 知道 `Output/bin/app.dcf` 是**烧录目标**，不是 .bin、不是 .rv32
- [ ] 知道 `Ctrl+F9` 背后是 gcc -c → link → objcopy → xmaker
- [ ] 知道 Add files 是 Project → 右键 → Add files recursively，**不是** Add directory
- [ ] 知道什么是 `riscv32` profile；能配会切换
- [ ] 知道 `.xm` / xmaker 是什么，9 条构建错误怎么解
- [ ] 知道 HUART 默认 PB3、115200 8N1

如果 6 项 ✅——你能独立 build、烧录、debug 工具链层面问题。**SDK 内部的"为什么飞"则去看 [03](03_SDK架构与运行模型.md)、[04](04_按键系统完全指南.md)、[05](05_PetitFatFs源码导读.md) 三篇。**
