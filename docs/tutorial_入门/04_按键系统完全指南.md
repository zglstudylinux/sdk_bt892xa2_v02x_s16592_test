## 1. 5 ms 扫描循环

### 1.1 ISR 概览

调用链（参考 [02 §1.4](02_BT892XA2芯片与外设地图.md)）：

```
每 5 ms
  ISR tmr5ms_thread()                       (在 bsp_sys.c 里)
  ├── bsp_key_scan()                        (在 bsp_key.c 里)
  │     ├── 读 SAR ADC (channel = 12, PB5 WKO)
  │     ├── 与 pwrkey_table[] walk，看落在哪一格
  │     ├── 与上一次比较，相同计数 +1
  │     ├── 不相同计数清 0
  │     ├── 当相同计数 ≥ KEY_SCAN_TIMES (=6)
  │     │     → msg_enqueue(key_id)
  │     └── 把当前 ADC 值缓到静态变量
  ├── 别的 500ms / 1s / SD 卡事件 ...
  └── 别的 callback
```

### 1.2 ADC 怎么读

```c
// 简化版，bsp_key_scan 实际是上面这逻辑
u16 wko_val = (u16)(SARADCDATA >> 2);  // 10-bit → 8-bit

// 但更准确说 wko_val 是 8-bit (key table 按 8-bit 分)
wko_val = (u16)((SARADCDATA >> 2) & 0xFF);   // 0..255
```

> 注：高精度（10 bit）也行，但 8-bit 跑表更稳、写起来简单。

### 1.3 频率 vs 时间

| KEY_SCAN_TIMES | 时间 |
|---|---|
| 1 | 5 ms（每次都发） |
| 3 | 15 ms |
| **6（默认）** | **30 ms 连续相同** |
| 12 | 60 ms（无障碍工坊、强烈推荐） |

默认 6。**改这个值要重启（改 `config.h`）**。

## 2. 分压电路：多个按键共用一根 ADC

### 2.1 全部按键一根线的原因

BT892XA2 上 **PB5（WKO）** 是一根**模拟 IO**——既能当普通 IO，又能当 SAR ADC channel 12。

**假设**有 N 个按键走 N 根 GPIO 中断，**会**：
- 占用 N 根 io（PBC 紧张的产品很痛）
- N 个独立的 ISR
- N 个 input pullup

**优化**：**多按钮 + 多电阻分压**到一根 ADC，按下产生唯一电压。

### 2.2 电路原理

```
                              VDD (3.3V)
                              │
                              ├─ 10K 内部上拉（SDK 默认；用 adcch_io_pu10k_enable）
                              │
                             PB5 (WKO/ADC channel 12) ────→ ADC 测这点电压
                              │
                              ├── 按键 S5 (0Ω 直通 GND)
                              ├── 按键 S6 (12K 下拉 GND)
                              └── 按键 S7 (47K 下拉 GND)
                              │
                              GND
```

**按下哪个 = 哪个电阻被连通**：

- 都不按：上拉=10K，没有下拉，Vadc = VDD = 3.3V，ADC ≈ 0xFF（满）
- 按 S5 (0Ω)：上拉=10K，被 0Ω 短路到 GND，Vadc ≈ 0V，ADC ≈ 0x00
- 按 S6 (12K)：上拉=10K + 下拉=12K 分压
    Vadc = 3.3V × 12K / (10K + 12K) ≈ 1.80V
    ADC ≈ 1.80 / 3.30 × 256 ≈ 0x8B（约 140/255）
- 按 S7 (47K)：上拉=10K + 下拉=47K 分压
    Vadc = 3.3V × 47K / (10K + 47K) ≈ 2.72V
    ADC ≈ 2.72 / 3.30 × 256 ≈ 0xD3（约 211/255）

### 2.3 完整按键映射（BT892XA2 Boombox 板）

| 按钮 | 电阻 | ADC 期望值 | 实测 |
|---|---|---|---|
| (无)        | 10K 上拉 / **无下拉**    | 0xFF | 0xFF (255) |
| S5 P/P     | **0Ω 直通**              | 0x00 | 0x00..0x0A (0..10)|
| S6 PREV    | **12K 下拉**             | 0x8B | 0x88..0x90 |
| S7 NEXT    | **47K 下拉**             | 0xD3 | 0xCE..0xD8 |

> 来源：`port_key.c:158-180` 注释 + `wav_test_03.md §5.1-5.2`

### 2.4 高阻源问题

| 电阻 | 源阻抗 | ADC 噪声 |
|---|---|---|
| 10K 内上拉 + 0Ω 下拉 | 0Ω（强下拉） | 几乎 0 |
| 10K 内上拉 + 12K 下拉 | 5.45K | 1-2 LSB |
| 10K 内上拉 + 47K 下拉 | 8.24K | 3-5 LSB |

**为什么**：源阻抗越大，ADC 内部采样电容充电越慢，未到稳态就读 → 抖动更大。

### 2.5 `saradc_setup_time_set` 是空宏

`api_saradc.h:10` 定义：
```c
#define saradc_setup_time_set(us)   /* noop */
```

注释说要**加建立时间**但**API 没实现**。后果：高阻源按键**没有**内置 ADC 缓冲时间。

**实际减缓办法**：
1. **阈值放宽**（下一节讲）
2. 自定义 `adcch_*_setup_time_set`（如果 SDK 提供）
3. 增强 ADC clock 慢一些（但 SDK 不一定能设）

## 3. `pwrkey_table[]` walk 算法（窗口上界）

### 3.1 真实表（12K/47K 板）

```c
// app/projects/standard/port/port_key.c:184-191
AT(.com_text.pwrkey.table)
const adkey_tbl_t pwrkey_table[6] = {
    {0x0A, KEY_PLAY},                   //PLAY/PAUSE  S5=0Ω   ADC ≤ 0x0A
    {0xA0, KEY_PREV},                   //PREV        S6=12K  ADC = 0x8B (139)
    {0xE5, KEY_NEXT},                   //NEXT        S7=47K  ADC = 0xD3 (211)
    {0xFF, NO_KEY},                     //未用 / NO_KEY
    {0xFF, NO_KEY},                     //未用 / NO_KEY
    {0xFF, NO_KEY},                     //未用 / 末尾
};
```

### 3.2 walk 算法（伪代码）

```c
u8 wko_val = ...; // 8-bit (0..255)
u8 num = 0;
while (wko_val > pwrkey_table[num].adc_val) {
    num++;
    if (num >= 6) break;      // 数组越界保护
}
// 现在 pwrkey_table[num] 就是命中
return pwrkey_table[num].key_id;
```

**关键理解**：`.adc_val` 是**窗口上界**，**不是中点**。

| 走的步 | 条件 | num |
|---|---|---|
| wko_val=0x05 | 不 > 0x0A, num=0 | 0 → KEY_PLAY |
| wko_val=0x8B | 0x8B > 0x0A 走; 不 > 0xA0 停 | 1 → KEY_PREV |
| wko_val=0xD3 | 0xD3 > 0x0A, > 0xA0; 不 > 0xE5 停 | 2 → KEY_NEXT |
| wko_val=0xFF | 0xFF > 0x0A, > 0xA0, > 0xE5, > 0xFF 走 | 3 → NO_KEY |

### 3.3 表的要求

| 要求 | 后果 |
|---|---|
| `.adc_val` **严格递增** | 否，走表跳不过去 |
| `.adc_val` **无重复** | 否，永远命中第一个 → 后面的死 |
| 末尾 = `0xFF` 或 `NO_KEY` | 让 idle (wko_val=0xFF) 落到 NO_KEY 槽 |
| `.adc_val` 不要超 0xFE | max 必须小于 0xFF |

### 3.4 walk 一次模拟

**情境**：按 S6 PREV，ADC 实测 0x8B。

```
num=0: wko_val=0x8B > pwrkey_table[0].adc_val=0x0A ? 是 → num++
num=1: wko_val=0x8B > pwrkey_table[1].adc_val=0xA0? 否 → 停
返回 pwrkey_table[1].key_id = KEY_PREV = 0x40
```

### 3.5 阈值到 key 的对应转换

walk 找到后，`.key_id` 是**plain 长按 key**（`KEY_PLAY=0x20` 等）—— 后面要 OR 上 `KU_/KH_/KL_*` 标志位。

详细的 OR 流程：

```
plain key 0x20 (KEY_PLAY)
    ↓ 检测到
   短按 → OR 0x800 → 0x820 (KU_PLAY)
   长按 → OR 0xA00 → 0xA20 (KL_PLAY)
   持续 → OR 0xE00 → 0xE20 (KH_PLAY)
```

(在 [§5](#5-ku_kh_kl_编码规则) 详)

## 4. 防抖数学：高阻源 30 ms 吞键怎么填

> 🚨 这一节是 Phase 5 Task 5.4 的**最大坑**，从这里弄明白了。

### 4.1 防抖逻辑

```
连续 6 次 (≈ 30ms) ADC 值落在同一格 → 才入队列
否则：计数清 0
```

### 4.2 低阻源：阈值贴实测没问题

例：S5 (0Ω)，实测 0x00-0x0A 抖动，**阈值给 0x0A** = 始终能命中第 0 格。

### 4.3 高阻源：阈值贴实测会丢键

S7 (47K)，实测 0xCE-0xD8 抖动。**如果你把阈值给 0xD3**：

| 扫描次数 | ADC 读 | 阈值 < 读吗? | 命中 |
|---|---|---|---|
| 1 | 0xD3 | 否 | KEY_NEXT |
| 2 | 0xCE | 是 | 落到 NO_KEY |
| 3 | 0xD5 | 否 | KEY_NEXT |
| 4 | 0xD2 | 是 | NO_KEY |
| 5 | 0xD6 | 否 | KEY_NEXT |
| 6 | 0xCF | 是 | NO_KEY |

6 次里只有 3 次在 KEY_NEXT，30 ms 防抖**永远不会触发**，按键**永远不入队列**——**症状**：按 S7 完全没反应。

### 4.4 修法：阈值留 ≥ 18 计数裕量

```c
{0xE5, KEY_NEXT},  // 实测 0xD3 → 阈值 0xD3 + 0x12 (18) = 0xE5
```

- 0xD3 ≤ 实测 0xCE-0xD8 全部 ≤ 0xE5 → walk 命中 KEY_NEXT
- 即使 ADC 漂到 0xE0（噪声加剧），仍然 ≤ 0xE5 ✓
- **余量 0xE5-0xD8 = 13** 个 LSB 噪声裕量

### 4.5 为什么 18 是个安全数

| 实测 ADC | 阈值给 | 裕量 |
|---|---|---|
| 0xD3 | 0xD3 | **0** (一定丢)|
| 0xD3 | 0xDA | 7 (濒临丢)|
| 0xD3 | 0xE0 | 13 (基本 OK)|
| 0xD3 | **0xE5** | **18 (稳)** |
| 0xD3 | 0xFF | 不可能 (撞 idle 边界) |

18 是实测的"必须 ≥ 16，宁可 18"。实际写时：
- **0Ω**：阈值给 `0x0A` (实测 ≤0x0A + 5 裕量)
- **12K**：阈值给 `0xA0` (实测 0x8B + 21 裕量)
- **47K**：阈值给 `0xE5` (实测 0xD3 + 18 裕量)

### 4.6 id zone 写法（debug 时更直观）

```
┌─ idle (未按) ──── 0xFF ──┐
│  zone 3: NEXT     ≤0xE5  │
│  zone 2: PREV     ≤0xA0  │
│  zone 1: PLAY     ≤0x0A  │
│  zone 0: short    ≤0x00  │
└──────────────────────────┘
```

每 zone 的"宽度"决定抗噪能力——zone 越宽，按键越稳，但**也**容易把邻近按钮误判。

## 5. `KU_*/KH_*/KL_*` 编码规则

### 5.1 三种行为

| 行为 | 缩写 | 标志位 | 长啥样 |
|---|---|---|---|
| 短按（release 时入队列）| KU_* (Key Up) | OR 0x800 | `KEY_PLAY \| 0x800` = 0x820 |
| 长按（按住 ~1.2 s 才入队列）| KL_* (Key Long) | OR 0xA00 | `KEY_PLAY \| 0xA00` = 0xA20 |
| 持续（按住不放，~~定期重发~~，过 1.2s 才一次） | KH_* (Key Hold) | OR 0xE00 | `KEY_PLAY \| 0xE00` = 0xE20 |

> 其实"持续"是按住超时后**再一次性** OR KH_ 入队列（不是定期重发）。

### 5.2 base id 范围

`bsp_key.h` 大约 100 个 plain key id：

| 范围 | 举例 | 用途 |
|---|---|---|
| 0x00-0x1F | NUM_* 数字键 | 一些 SDK 用 |
| 0x20-0x3F | PLAY, FF, FB | 音乐控制 |
| 0x40-0x5F | PREV, NEXT | 列表切换 |
| 0x60-0x7F | VOL_UP, VOL_DOWN | 音量 |
| 0x80-0x9F | POWER, MODE | 系统 |
| **0xE0-0xEF** | **PWR family** (USER_DEF 等) | **有特殊含义（§8 详）** |

### 5.3 KU_/KL_/KH_ 完整表

打开 `bsp_key.h:213-280`，能找到约 100 个定义：

```c
#define KU_PLAY                  (KEY_PLAY    | 0x800)   // 0x820
#define KU_NEXT                  (KEY_NEXT    | 0x800)   // 0x860
#define KU_PREV                  (KEY_PREV    | 0x800)   // 0x840
#define KU_VOL_UP                (KEY_VOL_UP  | 0x800)   // ...
// ... 几十个

#define KL_PLAY                  (KEY_PLAY    | 0xA00)   // 0xA20
#define KL_PREV                  (KEY_PREV    | 0xA00)
// ...

#define KH_PLAY                  (KEY_PLAY    | 0xE00)   // 0xE20
#define KH_PREV                  (KEY_PREV    | 0xE00)
// ...
```

> **关键**：base id + 标志位 = 真的 msg。你看到 `0x0820` 立刻能拆出来 `KU_PLAY`。

### 5.4 "组合"key（双功能）

例如 `KEY_NEXT_VOL_UP`：短按 = next, 长按 = vol+。

```c
#define KEY_NEXT_VOL_UP  0x???   // 普通 KID（不在 PWR 家族）
// short: KU_NEXT_VOL_UP = ... | 0x800 (短按当 next)
// long:  KL_VOL_UP_NEXT = ... | 0xA00 (长按当 vol+)
```

实际 KEY id 编码：

```c
// 短按 KU_NEXT_VOL_UP = 0x866 （KID=0x66 + 0x800）
// 长按 KL_VOL_UP_NEXT = 0xA66 （KID=0x66 + 0xA00）
//
// 注意：同一个 KID 走 short/long 处理两套宏：
// - KID = KEY_NEXT_VOL_UP 的 short KU_ 版本 → KU_NEXT_VOL_UP（按 short 走 next）
// - 同一个 KID 的 long KL_ 版本 → KL_VOL_UP_NEXT（按 long 走 vol+）
// SDK 内部逻辑：short/long 是分开的，调用者收到 KU 或 KL 就执行不同动作
```

> 容易混乱：`KU_*` 和 `KL_*` 不是"短路/长路切换"，而是**两套不同的行为配置**。

### 5.5 实际 debug log 看到的 key code

`wav_test.c` 收到 KU_PLAY = 0x820，跑：

```c
case KU_PLAY:
    s_paused = !s_paused;
    printf("[WAV] %s\n", s_paused ? "pause" : "resume");
    break;
```

输出去：

```
[WAV] key 0x0820 -> pause
```

拆 key code：0x0820 = 0x800 | 0x020 = KU_ | KEY_PLAY。

### 5.6 "我想绑定 KID 但要 KU/KL/KH 三个都接"

经常有人写：

```c
case KU_PLAY: case KL_PLAY: case KH_PLAY:
    /* 三个都管 */
```

这是错的——KH_PLAY 是"持续按住 1.2s 后才发一次"，长期按住**会重复发**。一般：

```c
case KU_PLAY:
    /* 短按：只看一次 release */
    break;
case KL_PLAY:
    /* 长按：可能在长按 1.2s 时触发 */
    break;
case KH_PLAY:
    /* 一般不接，除非你是"模式"  */
    break;
```

## 6. 系统事件过滤：`0x07xx` 一定要过滤

### 6.1 系统事件有哪些

`bsp_sys.c:441-460` 里塞进以下系统事件：

| 事件 | 值 | 谁产生 |
|---|---|---|
| `EVT_BT_UPDATE_STA` | 0x7D0 | Bluetooth stack |
| `EVT_BT_CONNECT`   | 0x7D3 | 同上 |
| `EVT_BT_DISCON`    | 0x7D4 | 同上 |
| `EVT_SD_REMOVE`    | 0x7FC | SD 卡拔出 |
| `EVT_SD_INSERT`    | 0x7FD | SD 卡插入 |
| `MSG_SYS_500MS`    | 0x7FE | 5ms ISR 计数 |
| `MSG_SYS_1S`       | 0x7FF | 同上 |

### 6.2 不过滤的后果

新手常见的错误：

```c
u16 msg = msg_dequeue();
if (msg == NO_MSG) return;
printf("[WAV] key 0x%04X -> ", msg);    // ← 打印会暴露噪声

switch (msg) {
    case KU_PLAY:
        // 永不命中！
        break;
}
```

输出（你按 100 次 PLAY 也看不到一次）：

```
[WAV] key 0x07FE -> ...   ← 500ms 一次噪声
[WAV] key 0x07FE -> ...
[WAV] key 0x07FE -> ...
[WAV] key 0x07FD -> ...   ← SD 卡插入事件
[WAV] key 0x07FE -> ...
...
```

**why?**：默认 case 吃掉所有消息，`switch (msg)` 里没有任何 case **没 default 的 fallback**。你按一次 KU_PLAY，**被 default 抢走**，啥效果都没。

### 6.3 过滤式（正确）

[wav_test.c:267](../tutorial_入门/04_按键系统完全指南.md) 的过滤式：

```c
if (msg < 0x0100 || (msg & 0xFF00) == 0x0700) {
    return;
}
```

**解释**：
- `msg < 0x100`：base key id 0x00-0xFF 不存在（普通 base 在 0x20-0xFF 之间）
- `(msg & 0xFF00) == 0x0700`：高 8 位 = 0x07 命中系统事件
- 两个 `||` 一起：非系统事件 + (有合法 base id) 才进 switch

**留给 KU_/KL_/KH_**：
- KU_* base | 0x800 → (msg & 0xFF00) = 0x0800 ≠ 0x0700 ✓
- KL_* base | 0xA00 → 0x0A00 ≠ 0x0700 ✓
- KH_* base | 0xE00 → 0x0E00 ≠ 0x0700 ✓
- msg = 0x820 → & 0xFF00 = 0x0800 ≠ 0x0700 ✓ pass
- msg = 0x7FE → & 0xFF00 = 0x0700 = 0x0700 ✗ 过滤
- msg = 0x0001 → msg < 0x0100 ✗ 过滤

### 6.4 调试技巧：分发前打

debug 时，**先把过滤改为"只打"看看队列里到底都有什么**：

```c
u16 msg = msg_dequeue();
if (msg != NO_MSG) {
    printf("[DBG] msg 0x%04X\n", msg);   // ← 看真实内容
}
```

跑 1-2 秒看 log：
- 全是 0x07FE / 0x07FD... = 队列被系统事件占满
- 偶尔 0x0820 / 0x0860 = KU_PLAY 等真按键

## 7. USER_PWRKEY 与 `xcfg_cb.user_pwrkey_en` 双开关

### 7.1 第一个开关：`config.h USER_PWRKEY`

```c
// app/projects/standard/include/config_extra.h 或 config.h
#define USER_PWRKEY  1     // 1 = 编入 pwrkey driver
```

**0 = 不编**：pwrkey_table / bsp_key_scan 那段代码**根本不存在**——所有"按键"都不可用。Build 也不会连接库。

### 7.2 第二个开关：`xcfg_cb.user_pwrkey_en`

```c
// xcfg.bin / Settings/Boombox.setting:121
xcfg_cb.user_pwrkey_en = 1;  // 1 = 运行时启用
```

**0 = 跳 key scan**：bsp_key_scan 里**有**，但**给一路 false 返回**，啥都不会塞队列。

### 7.3 两个都要开才工作

| USER_PWRKEY (config.h) | xcfg user_pwrkey_en | 行为 |
|---|---|---|
| 0 | 任意 | **代码根本不存在**，什么键都不可用 |
| 1 | 0 | 扫描里被 skip，no key 行为 |
| 1 | 1 | **工作** |
| 0 | 1 | 代码不存在，**开也没用** |

> 看到这里如果你误把 USER_PWRKEY 写成 0，烧入后再改 GUI xcfg **没用**——得 **rebuild**。

### 7.4 怎么检查（你当前是哪个）

**步骤 1：检查编译开关**：

打开 `app/projects/standard/include/config.h` 或 `config_extra.h`：

```powershell
grep -n 'USER_PWRKEY' app/projects/standard/include/*.h
```

应看到 `1`（不是 `0`）。

**步骤 2：检查运行时值**：

打开 Downloader UI，对应配置项翻成 `True`。

或读 `xcfg.bin`（如果 hex viewer）：

```
offset 121 ?
```

### 7.5 你最可能踩坑的现场

```c
// app/projects/standard/config_extra.h:101
#define USER_PWRKEY 0   // ← 默认关（Boombox 板开启）
```

**修**：把 `0` 改成 `1`，重 build。

## 8. KEY_PLAY_PWR_USER_DEF 陷阱

### 8.1 PWR family（0xE0-0xEF）

| Key id | 含义 |
|---|---|
| `KEY_PLAY_USER_DEF = 0xE1` | 短按 PLAY，长按/双击/三击 user-def |
| `KEY_PLAY_PWR_USER_DEF = 0xE2` | **短按 PLAY，** 长按 POWER |
| ... 还有 0xE3-0xEE ... |

特点：**长按 (`KLH_*` = KID|0xE00)** = 1.2s 触发关机的状态码。

### 8.2 自动软关机

```c
// app/platform/functions/func.c:298-310
case KLH_PLAY_PWR_USER_DEF:
    func_cb.sta = FUNC_PWROFF;     // 直接切到 func_pwroff
    break;
```

效果：长按带 `KEY_PLAY_PWR_USER_DEF` 的"PLAY 键"1.2 秒 → 板子软关机。

### 8.3 wav_test 怎么避坑

`wav_test.c` 用 `KEY_PLAY=0x20`（普通 PLAY，**不属 PWR 家族**）：

```c
// pwrkey_table
{0x0A, KEY_PLAY},   // ← 0x20 (普通 PLAY), 不是 0xE2 (PWR USER_DEF)
```

所以"P/P 长按 1.2 秒"只是发送 KL_PLAY = 0xA20，**不会**触发 FUNC_PWROFF。

### 8.4 怎么切回去

如果你**想**用 PWR 长按功能，把 `pwrkey_table[0]` 改成 `KEY_PLAY_PWR_USER_DEF`：

```c
{0x0A, KEY_PLAY_PWR_USER_DEF},   // ← 长按会重启
```

但**记得**：
- wav_test 里 `KU_PLAY_PWR_USER_DEF` 也进了 switch（见 [wav_test.c:280-285](../tutorial_入门/04_按键系统完全指南.md)）
- dispatch 路径 = **直接先软关机** → KLH_* 不会到你这 switch
- 短按 (KU_PLAY_PWR_USER_DEF = 0xE22) 照常进 pause/resume

### 8.5 这个陷阱的教训

> ⚠️ 用 PWR family 键 id 前，先在 func.c 里 grep `KLH_*` + `FUNC_PWROFF`——看是不是有"shadow"联动

## 9. 自定义板重设计 `pwrkey_table`

### 9.1 5 步

1. **看原理图**：每个按键的电阻（包括上拉）
2. **计算 ADC**：`Vadc = VDD * R_ext / (R_int + R_ext)`
3. **实测 ADC**：用 `examples/adc_single`（[02 §7](02_BT892XA2芯片与外设地图.md)）每个按键按 10 次取中位数
4. **加 18 LSB 裕量**（高阻源；低阻源 5 LSB）
5. **写表 + 测**：每按键按 50 次，看是不是都识别

### 9.2 计算工具

| R_ext (KΩ) | Vadc (V)   | ADC (8-bit) |
|------------|------------|-------------|
| 0          | 0.00       | 0           |
| 1.0        | 0.30       | 23          |
| 2.0        | 0.55       | 43          |
| 5.1        | 1.11       | 86          |
| 10         | 1.65       | 128         |
| 12         | 1.80       | 140         |
| 22         | 2.27       | 176         |
| 33         | 2.52       | 196         |
| 47         | 2.72       | 211         |
| 100        | 3.00       | 233         |
| ∞ (none)   | 3.30       | 255         |

> 实测会有 ±5% 漂移（电阻精度 + ADC offset）。**实测优于计算**。

### 9.3 用 sample 工具做完整模板

```c
// template_pwrkey_table.c — 给一个 4 键板子
/*
 * 原理图：
 *   S1 = 0Ω (P/P)
 *   S2 = 12K (PREV)
 *   S3 = 47K (NEXT)
 *   S4 = 100K (MODE)
 */
AT(.com_text.pwrkey.table)
const adkey_tbl_t pwrkey_table[6] = {
    {0x0A, KEY_PLAY},                          // S1 (实测 ≤ 0x0A)
    {0xA0, KEY_PREV},                          // S2 (实测 ≈ 0x8B + 21 裕量)
    {0xE5, KEY_NEXT},                          // S3 (实测 ≈ 0xD3 + 18 裕量)
    {0xF0, KEY_MODE},                          // S4 (实测 ≈ 0xE8 + 8 裕量；低端)
    {0xFF, NO_KEY},                            // 未用
    {0xFF, NO_KEY},                            // 末尾
};
```

> 如果 S4 实测 = 0xE8，想"足够宽裕"，可上推到 0xF3 = 实测 + 11。但**不能太接近 0xFF (idle)**——否则按了 S4 -> idle 漂到 0xFA -> 0xFF，可能跑掉。

### 9.4 调试技巧：临时加 debug 看 wko_val

`bsp_key.c` 主流程里有一行（被注释）：

```c
//    printf("%s enqueue key 0x%X wko_val = 0x%X\n", key_enqueue_str, key, wko_val);
```

**取消注释** 重 build 烧后，按每个键时 **能看到原始 ADC 值** + 入队码。

> 这种 deep debug 不常需要，先**前 4 步**。无解再去打开它。

## 10. 诊断日志技巧与 6 种"按键不响应"区分

### 10.1 6 种根因（按概率排）

| # | 根因 | 症状 | debug |
|---|----|------|-------|
| 1 | **系统事件过滤掉了**（[§6](#6-系统事件过滤0x07xx-一定要过滤)）| 按键 log 全无 | 看 `case KU_*` 是不是会被你 switch 命中 |
| 2 | **xcfg_cb.user_pwrkey_en=False**（[§7](#7-user_pwrkey-与-xcfg_cbuser_pwrkey_en-双开关)）| scan 返回永远 false | GUI 改 / hex 看 xcfg.bin:121 |
| 3 | **USER_PWRKEY=0**（[§7](#7-user_pwrkey-与-xcfg_cbuser_pwrkey_en-双开关)）| scan 代码根本不在 | 配置改 + rebuild |
| 4 | **47K 高阻源 0 裕量阈值被防抖吞**（[§4](#4-防抖数学高阻源-30-ms-吞键怎么填)）| NEXT 不响应 | 阈值 +18 LSB |
| 5 | **pwrkey_table[] 阈值错位**（[§3](#3-pwrkey_table-walk-算法窗口上界)）| 短按 KEY_UNKNOWN | debug 看 wko_val；重新算 |
| 6 | **pwrkey 误用了 PWR family → 长按 -> FUNC_PWROFF**（[§8](#8-key_play_pwr_user_def-陷阱)）| 按 1-2 秒重启 | 改 plain key id |

### 10.2 区分法（决策树）

```
start
│
├─ 串口 log 有 msg 0x0820 (KU_PLAY)?
│   │
│   ├─ NO → 检查 (1) 系统事件过滤、 (2) xcfg en、 (3) USER_PWRKEY=1
│   │
│   └─ YES → 走 case KU_PLAY code 跑了？
│              │
│              ├─ 没跑 → switch 没 case KU_PLAY → 加 case
│              │
│              └─ 跑了但没效果 → 检查 case 里的逻辑:
│                  - 双开关、用户态处理、mask
```

### 10.3 输出诊断 log

```c
// wav_test.c 风格
static void wav_test_handle_key(u16 msg)
{
    if (msg < 0x0100 || (msg & 0xFF00) == 0x0700) {
        // 不打, 不让噪声塞 log
        return;
    }
    printf("[WAV] key 0x%04X -> ", msg);    // 现在只会打到真键
    // switch...
}
```

### 10.4 "按了键板子立刻重启"

| 现象 | 什么键 id |
|---|---|
| 按 1.2 秒重启 | KEY_PLAY_PWR_USER_DEF (**长按触 FUNC_PWROFF**) |
| 按立刻重启 | `WDT` 没喂（不是键问题） |
| 按一秒后重启 | **WDT 分裂**——你的主 loop 没 WDT_CLR |

### 10.5 完整诊断脚本

```c
// examples/key_diag.c —— 打印每个键的 raw ADC + 命中 ID
#include "include.h"
AT(.text.key.init)
void key_diag_run(void) {
    gpio_t led;
    bsp_gpio_cfg_init(&led, IO_PD0); // 任意一个 LED
    cfg_initialized = 1;

    for (;;) {
        u16 msg = msg_dequeue();
        if (msg != NO_MSG) {
            printf("[KEY_DBG] msg 0x%04X\n", msg);
            bsp_gpio_set(&led, 1);   // 任何 cmd 亮一下
            delay_5ms(20);
            bsp_gpio_set(&led, 0);
        }
        WDT_CLR();                   // 必须
        delay_5ms(20);
    }
}
```

把这个烧进去，逐个按键按，看 log：
- 没任何 msg → 1 (系统事件没过滤) / 2 (en=False) / 3 (USER_PWRKEY=0)
- 有 msg 但 ID 错（意料外的数字）→ 4 (47K 裕量) / 5 (表错位)
- ID 对但代码不响应 → 6 (PWR family) / 7 (你 switch 没 case)

## 总结：核心清单

读完本篇后，**最少要保证**：

- [ ] 能解释 BT892XA2 **为什么用 1 根 ADC 分压**（不是每键单独 GPIO）
- [ ] 能正确**计算每按键预期 ADC**——简单分压
- [ ] 知道 `.adc_val` 是**窗口上界**，表必须**严格递增**且末尾要 `0xFF/NO_KEY`
- [ ] **每个高阻源按键阈值 + ≥ 18 LSB 裕量**
- [ ] **过滤 0x07xx 系统事件**——`if (msg < 0x100 || (msg & 0xFF00) == 0x0700) return;`
- [ ] 双开关 `USER_PWRKEY=1` + `xcfg_cb.user_pwrkey_en=1` 都开
- [ ] 知道 **PWR family**（0xE0-0xEF）长按 1.2 s 触发 FUNC_PWROFF
- [ ] 看到 `0x0860` 立刻能拆：0x0860 = KU_ | KEY_NEXT（[04 §5](04_按键系统完全指南.md) 字典）

如果 8 项 ✅——你能诊断任何按键不响应 / 按了重启 / 按键错位 / 加新键场景。
