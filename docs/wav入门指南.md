## 1. 为什么要懂 WAV 格式？

### 1.1 裸 PCM 长什么样

**PCM**（Pulse Code Modulation，脉冲编码调制）就是声音最原始的数字形式——把喇叭该振多高，一个采样一个采样记成整数。16-bit 立体声、44100 Hz 的一秒钟声音 = `44100 × 2 声道 × 2 字节 = 176400` 字节的纯数字。

如果你手上只有这一坨裸 PCM，那你其实**已经可以播**——一帧一帧推给 DAC 就行（§5 会讲怎么推）。问题是：磁盘上的 `.wav` 文件**不是**裸 PCM。

### 1.2 直接把整个文件倒进 DAC 会怎样

假设你偷懒，`pff_open("TEST.WAV")` 之后从头到尾 `pff_read` 一路读、一路推 `AUBUFDATA`：

```c
// ❌ 反例：把整个文件字节流当 PCM 推
while (pff_read(buf, sizeof(buf), &n), n) {
    push_to_dac(buf, n);   // 从第 0 字节开始推
}
```

你会踩到一连串问题：

| 问题 | 原因 |
|---|---|
| 开头"咔"一声杂音 | 文件前 44+ 字节是**文件头**（`RIFF`/`fmt `/`data` 标签、块大小、采样率…），不是音频，当采样推出去就是噪声 |
| 不知道音频从第几字节开始 | `data` **不一定**在偏移 44（中间可能塞 `LIST`/`fact`/`JUNK`），硬编码就会读错位置 |
| 速度不对（变快 / 变慢） | 你不知道采样率，DAC 采样率没对上 WAV 头，就会快放或慢放 |
| 声道错乱、左右不平衡 | 你不知道是单声道还是立体声，帧打包方式不同，推错就"一边响一边哑" |
| 全是噪声 | 你不知道位深，16-bit 采样被当成别的宽度解释，整段变噪声 |

这就像**只有硬盘却没有文件系统**——你面对一坨字节，找不到、也管不明白。所以第一步永远是：**先解析头，搞清楚"音频从哪开始、采样率多少、几个声道、多少位"，再去推数据。**

→ 想让歌正确出声，必须先读懂 WAV 这个"容器"。

## 2. WAV = RIFF 容器

### 2.1 RIFF 与 chunk（区块）

WAV 遵循 **RIFF**（Resource Interchange File Format）规则，以"区块 **chunk**"为最小存储单位。每个 chunk 的骨架都一样：

```
+--------------+------------------+--------------------------+
| FourCC (4B)  | 数据长度 (4B)      | 数据体 (长度个字节)         |
| 区块标签      | 小端 u32          | 真正的内容                 |
+--------------+------------------+--------------------------+
```

- **FourCC** = 4 个 ASCII 字符的标签，比如 `'fmt '`（注意末尾有个空格）、`'data'`。
- 紧跟 4 字节**小端** u32，表示后面数据体有多长。
- 播放器**只关心两个 chunk**：`fmt `（格式信息）和 `data`（PCM 音频）。中间的 `LIST`（歌名/歌手）、`fact`、`JUNK` 全部按标签跳过即可。

### 2.2 小端字节序（little-endian）

RIFF 里所有多字节数值都是**小端**存储——低位字节在前。读采样率、块大小时务必按小端解释：

```
磁盘上： 44 AC 00 00
小端还原：0x0000AC44 = 44100
```

技巧：读进来的原始 buffer 可以直接用**共用体 (union)** 或指针强转一次性还原，不必逐字节移位——§5 会看到立体声帧就是靠这一招"零处理"直推的。

### 2.3 三个核心 chunk + 文件布局图

一个最小可播的 WAV，头部固定这样排：

```
偏移
0x00  +----------------------------------+
      | 'RIFF'  (0x46464952)             |  ← 文件魔数，恒定
0x04  | 文件总长 - 8  (小端 u32)           |
0x08  | 'WAVE'  (0x45564157)             |  ← 声明这是 WAVE
0x0C  +----------------------------------+
      | 'fmt '  区块                      |
      |   长度 = 16                       |  ← 格式信息：声道/采样率/位深…
      |   wFormatTag / nChannels / ...    |
      +----------------------------------+
      | (可能有 LIST / fact / JUNK ...)   |  ← 播放器跳过
      +----------------------------------+
0x??  | 'data'  区块                      |
      |   长度 = PCM 总字节数              |
      |   [PCM 采样…交错 L/R…]            |  ← 真正要推给 DAC 的
      +----------------------------------+
```

**关键坑：`data` 不一定在偏移 44。** 很多 WAV 会在 `fmt ` 和 `data` 之间插 `LIST`/`fact`/`JUNK`。**绝不能硬编码 `lseek(44)`**，必须用 **chunk walker**（区块遍历器）按标签逐块跳：

```c
// wav_test.c 的 chunk 遍历器（:247-271），从偏移 12 开始
u32 pos = 12;
while (pos + 8 <= fsize) {
    pff_lseek(pos);
    pff_read(hdr, 8, &br);          // 读 8 字节区块头
    u32 chunk_size = rd32(hdr + 4); // 小端还原长度
    if (hdr[0]=='d'&&hdr[1]=='a'&&hdr[2]=='t'&&hdr[3]=='a') {
        data_offset = pos + 8;      // 命中！PCM 从这里开始
        data_size   = chunk_size;
        break;
    }
    pos += 8 + chunk_size + (chunk_size & 1);  // 跳到下一块
}
```

那个 `(chunk_size & 1)` 是 RIFF 的**字对齐填充**——区块长度是奇数时，后面补 1 个填充字节让下一块从偶数地址开始，遍历时要把它一起跳过。

## 3. `fmt ` chunk 逐字段

`fmt ` 区块 = 8 字节区块头（`'fmt '` + 长度）+ 16 字节格式体。把这 8 个位置逐个拆开：

| 字段 | 类型 | 含义 |
|---|---|---|
| FourCC | 4B | 固定 `'fmt '`（末尾一个空格） |
| 区块长度 | u32 | PCM 时为 `16` |
| `wFormatTag` | u16 | 编码格式，**`1` = PCM**；其它值是压缩格式（ADPCM / MP3-in-WAV…），本项目不支持 |
| `nChannels` | u16 | 声道数：`1` 单声道 / `2` 立体声 |
| `nSamplesPerSec` | u32 | 采样率（Hz），如 `44100` |
| `nAvgBytesPerSec` | u32 | 每秒字节数 = 采样率 × 块对齐 |
| `nBlockAlign` | u16 | 块对齐 = 声道数 × 位深 / 8 |
| `wBitsPerSample` | u16 | 采样位数，本项目只支持 **16** |

因为这 16 字节在内存里连续，实际代码可以"直接读进一个结构体"再按成员取值。

### 3.1 用真实 TEST.WAV 做对照

我们实测的 `TEST.WAV`：文件大小 `52,920,044` 字节（Part 1 串口打印 `file size=52920044`，且 RIFF size 字段 `52920036` = 文件 − 8，两者互证），PCM / 44100 Hz / 16-bit / 立体声。下面是 [wav_test_01.md](wav_test_01.md) §3 实测串口打印的头部 64 字节 hex dump，逐字段对照（hex 全部摘自真实 dump）：

| 偏移 | 磁盘 hex（小端） | 解码值 | 字段 / 含义 |
|---|---|---|---|
| 0x00 | `52 49 46 46` | `RIFF` | ChunkID 魔数（`0x46464952`） |
| 0x04 | `E4 7E 27 03` | 52,920,036 | RIFF 块大小 = 文件 − 8 |
| 0x08 | `57 41 56 45` | `WAVE` | 格式标识 |
| 0x0C | `66 6D 74 20` | `fmt ` | 第一个子块：格式块 |
| 0x10 | `10 00 00 00` | 16 | `fmt ` 块长度 |
| 0x14 | `01 00` | `0x0001` | **wFormatTag = PCM** |
| 0x16 | `02 00` | 2 | `nChannels`（立体声） |
| 0x18 | `44 AC 00 00` | 44100 | `nSamplesPerSec`（44.1 kHz） |
| 0x1C | `10 B1 02 00` | 176400 | `nAvgBytesPerSec` |
| 0x20 | `04 00` | 4 | `nBlockAlign` |
| 0x22 | `10 00` | 16 | `wBitsPerSample` |
| 0x24 | `64 61 74 61` | `data` | 第二个子块：数据块（紧跟 `fmt `，无 LIST/JUNK） |

因为 `data` FourCC 在 0x24、区块头 8 字节，所以 `data_offset = 0x24 + 8 = 0x2C = 44`——PCM 正好从第 44 字节开始。这是 [wav_test_01.md](wav_test_01.md) 实测跑出来的解析结果（串口逐字打印）：

```
[WAV]   chunk @0x0C: fourcc = fmt , size = 16
[WAV]   fmt chunk contents:
[WAV]     wFormatTag        = 0x0001 (PCM)
[WAV]     nChannels         = 2
[WAV]     nSamplesPerSec    = 44100 Hz
[WAV]     nAvgBytesPerSec   = 176400
[WAV]     nBlockAlign       = 4
[WAV]     wBitsPerSample    = 16
```

### 3.2 字段互相验证（很好的自检习惯）

`fmt ` 里几个字段不是独立的，能互相印证——解析完顺手对一遍，错了立刻发现：

```
块对齐    nBlockAlign     = 声道 × 位深/8 = 2 × 16/8 = 4        ✓（dump = 4）
每秒字节  nAvgBytesPerSec = 采样率 × 块对齐 = 44100 × 4 = 176400 ✓（dump = 176400）
时长      = data 长度 / nAvgBytesPerSec（data 长度运行时读，见下）
         粗估：文件 52.9 MB ÷ 176400 ≈ 300 秒 ≈ 5 分钟（若整段皆 PCM）
```

`nBlockAlign` 和 `nAvgBytesPerSec` 两条算术能和 dump 里的字段严丝合缝对上，说明解析没跑偏——这两条是**可验证的硬事实**。时长要用 `data` 区块长度除以 `nAvgBytesPerSec`；本文件按总大小**粗估**约 5 分钟。注意：头里存的 `data` 长度字段（0x28，本文件是 `C3 00 C4 00`）由生成工具写入，运行时才读出使用，不同工具产出的 WAV 此字段未必与文件实际大小完全一致，所以时长以运行时读到的为准，别把它当成精确值。

## 4. `data` chunk 里 PCM 是怎么排的

### 4.1 帧 = 一次采样的全部声道

`data` 区块标签后紧跟 4 字节长度，再往后（本文件是偏移 44）才是 PCM。16-bit 立体声的排布是**声道交错 (interleaved)**——左右声道**轮流**存，每个采样 2 字节：

```
一帧 (frame) = 一个时刻所有声道的采样
立体声一帧 = L(2B) + R(2B) = 4 字节，磁盘上按字节是：

  +------+------+------+------+
  | L_lo | L_hi | R_lo | R_hi |   ← 小端，低字节在前
  +------+------+------+------+
   \___ Left 16-bit ___/\___ Right 16-bit ___/

data 里就是： [帧0][帧1][帧2]... = L R L R L R ...
```

单声道则每帧只有 1 个 2 字节采样：`[S][S][S]...`。

### 4.2 采样是"有符号 16-bit 小端"

这是最容易搞错、也最要命的一点：

- **有符号 (signed)**：采样值绕 `0` 振荡，`0x0000` = 静音，正峰是 `0x7FFF`（+32767），负峰是 `0x8000`（−32768）。**不要**做 `^ 0x8000` 之类的"有符号↔无符号"转换——DAC 要的就是有符号原值（§6 会看到这个转换正是我们踩过的坑）。
- **16-bit**：每采样正好 2 字节。24/32-bit 的源要先在电脑上转成 16-bit（见 §6）。
- **小端**：`7A 0A` = `0x0A7A` = 2682，不是 `0x7A0A`。

### 4.3 三个头字段决定怎么放

| 字段 | 决定了什么 | 放错的后果 |
|---|---|---|
| `nSamplesPerSec` | DAC 每秒吐多少帧 | 对不上 → 变速（快放 / 慢放） |
| `wBitsPerSample` | 每采样几字节、怎么取 | 对不上 → 全是噪声 |
| `nChannels` | 一帧几个采样、怎么打包 | 对不上 → 声道错乱 / 左右失衡 |

`data` 长度是读取上限——读满 `data_size` 字节就是歌放完了（也可以用 `pff_read` 实读字节数 `br` 是否小于请求字节数来判断到没到尾）。

## 5. 从 WAV 字节到 DAC 出声

### 5.1 整条播放流水线

```
SD 卡 ──▶ pff_open ──▶ 读头 / 解析 fmt ──▶ chunk walker 找 data
                                                  │
                        ┌─────────────────────────┘
                        ▼
  采样率 → SPR 枚举 ──▶ 唤醒 DAC ──▶ pff_lseek(data_offset)
                                          │
                                          ▼
             循环 pff_read(s_pcm) ──▶ 推 AUBUFDATA ──▶ 喇叭出声
                        ▲                    │
                        └── while(AUBUFCON & BIT(8)){}  满就等，天然限速
```

### 5.2 核心：`AUBUFDATA` 一次写入 = 一整帧

这是整个播放器的"命门"，务必记牢——DAC 的数据寄存器 `AUBUFDATA`（`SFR1_BASE + 0x01*4`）**一次接收一个 `u32`，一个 `u32` 写入就是一整个立体声帧**：

```
一个 u32 写进 AUBUFDATA：
  bit31 ....................... bit16 | bit15 ...................... bit0
  [        Right（WAV 第 2 声道）      | [        Left（WAV 第 1 声道）     ]
          高 16 位                              低 16 位

  → 低 16 = Left，高 16 = Right，两个都是有符号 16-bit，原样推，无偏移无异或
```

配一个满位门控：`AUBUFCON` 的 **BIT(8) == 1 表示 DACBUF（约 2 KB 的 FIFO）已满**；每次写之前先 `while (AUBUFCON & BIT(8)) {}` 等它清零。这一等就天然把推送节奏卡在实时速率上，不需要额外 `delay`。

这套用法在 SDK 里有三处独立印证：正弦测试表（`bsp_iis_ext.c` 每次取一个 `u32`/帧，表数据绕 `0x0000` 振荡带负值 → 证明有符号无偏移）、ADC→DAC 直通（`func_speaker.c` 的 `((u32)s<<16)|s`）、以及前辈心得"推 PCM 可以直接强转 32 位、偏移量 4、缓冲长度除 4"。（前两处是 `#if 0` 里的寄存器用法范式；真正常驻的直推活代码是 `bsp_iis_ext.c` 的 IIS-RX 回调 `while((AUBUFCON&BIT(8))==0) AUBUFDATA=*ptr32++;`，写法一致。详见 [wav_test_02.md](wav_test_02.md) §3。）

### 5.3 立体声为什么"零处理"直接推

回到 §4.1 那张帧图——磁盘上一个立体声帧是 `[L_lo L_hi R_lo R_hi]`（小端）。把这 4 字节**当作一个小端 `u32` 读出来**会得到什么？

```
磁盘字节： L_lo L_hi R_lo R_hi
小端 u32：(R_hi R_lo L_hi L_lo) = (R << 16) | L
                                = 高 16 位是 R，低 16 位是 L
                                = 正好就是 AUBUFDATA 要的帧格式！
```

所以**立体声播放不需要任何逐样本处理**——把读进来的缓冲直接 `(const u32 *)` 强转，一帧一推即可：

```c
/* 现行 wav_test.c:408-428 —— 一 u32 = 一帧，有符号原样推 */
if (nChannels == 2) {                    /* 立体声：[L_lo L_hi R_lo R_hi] LE == (R<<16)|L */
    u32 frames = n / 4;
    const u32 *src = (const u32 *)(const void *)s_pcm;
    for (u32 i = 0; i < frames; i++) {
        while (AUBUFCON & BIT(8)) { }    /* BIT(8)=1 满，等它清零 */
        AUBUFDATA = src[i];              /* 一次写入 = 一整帧，直推 */
    }
} else {                                 /* 单声道：同一采样复制进 L(低16) 与 R(高16) */
    u32 frames = n / 2;
    for (u32 i = 0; i < frames; i++) {
        u16 s = rd16(s_pcm + 2 * i);
        u32 v = ((u32)s << 16) | s;      /* R = L = s */
        while (AUBUFCON & BIT(8)) { }
        AUBUFDATA = v;
    }
}
```

### 5.4 采样率要给 SPR 枚举，不是给 Hz

DAC 用 `dac_spr_set()` 设采样率，但它的**实参是 `SPR_*` 枚举下标，不是原始 Hz**——传 `SPR_44100` 而不是数字 `44100`（`SPR_48000` 恰好 `== 0`，`SPR_44100 == 1`）。所以要拿 WAV 头的 Hz 查一张映射表：

| WAV 头采样率 (Hz) | `dac_spr_set()` 实参 | 枚举下标 |
|---|---|---|
| 48000 | `SPR_48000` | 0 |
| 44100 | `SPR_44100` | 1（我们的 `TEST.WAV`） |
| 38000 / 32000 | `SPR_38000` / `SPR_32000` | 2 / 3 |
| 24000 / 22050 | `SPR_24000` / `SPR_22050` | 4 / 5 |
| 16000 / 12000 | `SPR_16000` / `SPR_12000` | 6 / 7 |
| 11025 / 8000 | `SPR_11025` / `SPR_8000` | 8 / 9 |
| 其他（如 96000） | —— | 映射函数返回 `0xFFFF`（不支持，需先在 PC 上重采样） |

对应 `wav_test.c:94` 的 `wav_sample_rate_to_spr()`，未命中返回 `0xFFFF`。**采样率没设对，就会变速**（§6）。（枚举里其实还有 `SPR_96000` 等更高档位，只是本项目的映射表没收，需要时可自行补。）

### 5.5 DAC 唤醒序列

推数据之前得先"叫醒"DAC，否则模拟输出是哑的：

```c
/* wav_test.c:335-338 */
dac_set_dvol(DIG_N0DB);        /* 数字音量寄存器默认 0 = 静音！必须设成 0dB 满刻度 */
bsp_change_volume(sys_cb.vol); /* 模拟音量 */
dac_fade_in();                 /* 淡入 */
dac_fade_wait();               /* 等淡入完成 */
```

两件事最关键：

1. **`dac_set_dvol(DIG_N0DB)` 必须调**——数字音量寄存器上电默认是 `0`（静音），不显式拉到满刻度，后面推再多数据模拟口也没声（这正是早期版本"没声音"的原因）。
2. **`dac_fade_in()` → `dac_fade_wait()` 放在最后收尾**。

（数字音量与模拟音量两个调用谁先谁后不影响结果，SDK 参考实现里两种顺序都出现过；真正要记的是"dvol 必调 + fade 收尾"。）

```

[WAV] (direct AUBUFDATA push, polling AUBUFCON bit 8)
```

2026-07-29 实测：**第一次跑就正确出声，左右声道均衡、人声清晰。** 完整解析 + 播放的过程与踩坑复盘在 [wav_test_02.md](wav_test_02.md)。

## 6. 常见坑（前辈踩过的，照着避）

### 6.1 声道打包错误——本项目最痛的一个坑

早期版本没吃透"一 `u32` = 一帧"，写成了**每帧推两次、每次只把一个声道放进高 16 位、低 16 位填 0，还多做了个 `^ 0x8000`**：

```c
/* ❌ 旧版（错误）—— 症状：左声道明显更轻，人声糊成一团 */
u32 ul = ((u32)l ^ 0x8000) << 16;  /* 错1：^0x8000 把有符号→无符号，注入直流/回绕失真 */
u32 ur = ((u32)r ^ 0x8000) << 16;  /* 错2：<<16 使低 16 位 = 0 —— 而低 16 就是一整帧的左半 */
AUBUFDATA = ur;   /* 这其实是"一帧"：左半(低16)=0 静音，右半=乱码 r */
AUBUFDATA = ul;   /* 又"一帧"：左半=0 静音，右半=乱码 l —— 每帧一写变两写，2× 帧率 */
```

因为**一个 `u32` 就是一整帧（低 16=L，高 16=R）**，这两次写各自都是一整帧，而它们的**左半（低 16 位）恒为 0**：

| 现象 | 机理 |
|---|---|
| 左声道明显更轻 | 每帧的左半永远喂 0 → 一个物理声道近乎静音 |
| 人声糊、旋律还能听 | 另一半以 2× 帧率收到 `R,L,R,L` 交织，混成浑浊"伪单声道"；居中人声（需 L/R 相干等值）被抹糊，硬声像的乐器旋律尚能辨认 |
| `^ 0x8000` | 把有符号采样错当无符号，注入直流偏置 / 回绕失真 |

**修复**：回到 §5.3——立体声 `(const u32 *)` 强转直推、单声道复制进高低 16 位，有符号、无异或。改完一次跑通。完整踩坑复盘（含中途误诊成"L/R 互换"的弯路）见 [wav_test_02.md](wav_test_02.md)。

### 6.2 其它现场坑

| 坑 | 结论 | 出处 |
|---|---|---|
| **SD/TF 波特率要高** | 太低会推出"噗噗噗"杂音 / underrun。杜工：2M 以上才正常；李宗霖：起码拉到 8M，实跑 12M；李坪臻：16M 可以，17M 就出问题 | 杜工 / 李宗霖 / 李坪臻 |
| **读缓冲 ~512B 是甜点** | 太小音质会杂；512B 读+推音质很好 | 杜工 / 李宗霖 |
| **及时清 / 填缓冲** | SD 读取路径里别放 ms 级 `delay`、别对大数组慢速 `memset`，会饿死 DACBUF | 李宗霖 / 杜工 |
| **DAC 采样率必须匹配 WAV 头** | 否则快放 / 慢放；且与声道数相关，最好每首动态匹配（见 §5.4） | 李宗霖 / 袁福煜 |
| **24/32-bit 压 16-bit 音质差** | 直接用 16-bit 源，别指望板上降位 | 姚嘉隆 / 李坪臻 |
| **Petit FatFs 只认 8.3 短文件名** | 无 LFN，文件名用 `PLAY.WAV` 这种，长名会读成乱码 | 李光超 |
| **本平台无硬件浮点 / 无 libgcc** | 淡入淡出、进度百分比等数学一律用整数实现 | 金国强 |

## 7. 怎么自己生成 / 检查 WAV

### 7.1 生成一个"保证能播"的 WAV

目标格式：**16-bit PCM、44100 Hz、单声道或立体声、8.3 文件名**。

```bash
# ffmpeg：把任意音频转成 16-bit PCM 立体声（pcm_s16le = signed 16-bit little-endian）
ffmpeg -i input.mp3 -ac 2 -ar 44100 -f wav -acodec pcm_s16le PLAY.WAV

# 或 sox
sox input.mp3 -r 44100 -c 2 -b 16 PLAY.WAV

# 造一个 5 秒 440Hz 正弦纯音（最适合首次自测：波形干净，出错一耳朵能听出来）
ffmpeg -f lavfi -i "sine=frequency=440:duration=5" \
       -ac 2 -ar 44100 -f wav -acodec pcm_s16le PLAY.WAV
```

Windows 上用 **Audacity**：生成 → 音调（或导入音频）→ 文件 → 导出 → WAV（Microsoft）16-bit PCM。

**注意**：QQ 音乐等下载的 `.wav`/`.mp3` 可能被加密，放不出声——用 Audacity 自己生成正弦 / 方波来自测更靠谱。

### 7.2 用十六进制工具核对头

生成后，别急着烧板，先用十六进制编辑器看一眼头对不对：

| 平台 | 工具 |
|---|---|
| Windows | [HxD](https://mh-nexus.de/en/hxd/)、WinHex |
| Linux / macOS | `xxd PLAY.WAV \| head`、`hexdump -C PLAY.WAV \| head` |

按 §3.1 的对照表逐字节核：开头必须是 `52 49 46 46`（`RIFF`）、偏移 8 是 `57 41 56 45`（`WAVE`）、偏移 0x14 是 `01 00`（PCM）、采样率 / 位深 / 声道数是不是你要的。再顺手做一遍 §3.2 的两条互验算术，全对再拷进 SD 卡根目录（**不是子目录**，8.3 文件名）。

## 一句话总结

> WAV 不是裸 PCM，而是 **RIFF 容器**——先按 chunk 遍历器找到 `fmt `（拿采样率/声道/位深）和 `data`（`data` 位置不定，绝不能硬编码 44），再走"采样率→`SPR_*` 枚举 → `dac_set_dvol` 唤醒 → `pff_lseek(data)` → 循环 `pff_read` → 推 `AUBUFDATA`"这条流水线；而全场命门是 **一个 `u32` 写入 `AUBUFDATA` == 一整帧、低 16=Left / 高 16=Right、两个都是有符号 16-bit 原样推、写前轮询 `AUBUFCON & BIT(8)`**——磁盘上 `[L_lo L_hi R_lo R_hi]` 小端重解释成 `u32` 恰好就是 `(R<<16)|L`，所以立体声零逐样本处理直接强转直推。当年正是没吃透这一点、把一帧拆成两写又多了个 `^0x8000`，才有了"左声道更轻、人声糊"的经典翻车——想通"一 u32 一帧"，2026-07-29 第一次就跑通了左右均衡、人声清晰的整首歌。
